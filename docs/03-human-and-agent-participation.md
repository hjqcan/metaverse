# 人类与 agent 参与：共同生活、权限和预算

日期：2026-10-25

状态：讨论整理与设计建议，尚未实现或完成参与体验验证。

关联：[项目章程](00-project-charter.md)、[经济与资源](02-economy-and-resources.md)、[agent 研发闭环](04-agent-rnd-loop.md)。

## 1. 参与目的与已经确认的方向

用户确认世界同时容纳人类与 agent。人类可以创造、劳动，也可以只游玩；agent 也不被限定为劳动工具。世界不以证明人类劳动不可替代为目标，不要求所有居民持续生产才有资格留下。

用户明确提出的研发主线是：世界外的 agent 调研并得出方案，其他 agent 在外部构建候选版本，另一批测试 agent 入驻世界活动，再把构建与测试结果反馈给外部调研团队，持续完善方案。居民自己提出需求或发起研发，可以是未来选项；不能把它改写成当前已经确认的主线。

本文建议区分参与身份、控制方式、经济归属和研发职责。分开这些概念，才能允许灵活协作，又不把所有自动活动都混成“玩家增长”。

## 2. 居民身份与控制器分离

居民身份表示世界持续记录的主体：名称、历史、所属组织、资产和授权关系。控制器表示某一时间由谁产生动作：人类客户端、规则程序或模型 agent。二者不必一一固定。

可考虑让人类将部分事务委托给 agent，例如维护花园、安排演出或运输材料；也可以保留一个独立 agent 居民，由明确的所有者或组织提供预算。是否允许控制器在同一居民身份下切换，需要通过体验和权限实验决定，不应仅为技术方便默认开放全部权限。

建议保存以下关系：

| 信息 | 用途 |
| --- | --- |
| 居民身份 | 关联持续历史、世界内资产与互动 |
| 控制器及会话 | 解释此次动作来自人类、程序还是模型 |
| 所有者或授权主体 | 确定谁能授予、撤销和承担费用 |
| 实际控制分组 | 识别平台内部交易或同一主体的多个 agent |
| 权限、期限与预算 | 限定允许执行的动作和可支配资源 |
| 所在环境与规则版本 | 区分正式、测试及不同世界的动作语义 |

公开展示可以说明对方是 agent、平台服务或受委托角色；内部审计信息不必全部向其他居民暴露。控制关系无法确认时应标记未知，不能只因为使用不同账号就声称它们属于独立主体。

## 3. 两种入口，同一套动作规则

建议人类通过图形、语音等客户端参与，agent 通过原生 API 观察和行动。两种入口最终调用同一套权威动作验证：是否有权限、材料是否足够、目标是否可达、制造是否占用设备、交易是否已经完成。

原生 API 可以降低 agent 的交互成本，但不能隐含“读取整个数据库”或“直接修改世界状态”的权限。agent 发出移动、建造、交易等意图，规则层接受或拒绝，再产生可审计的状态变化。重试请求不能重复扣款或重复制造。

同规则不等于每个入口具有完全相同的显示方式和操作速度。哪些结构化数据提供给 agent、哪些也提供给人类辅助界面，需要按玩法定义；竞技、谜题等场景还应明确自动化资格和信息范围。不能先给予 agent 全知观察，再把结果解释为正常玩家体验。

## 4. agent 能看到什么

建议把观察信息分为公共、居民可感知、所有者私有、组织授权和运营调试几类。一个居民 agent 可以读取自己的库存和许可范围内的场景信息；不能因为采用了模型，就获取邻居私有资产、未公开地图、其他玩家输入或完整研发日志。

观察结果可以携带时间、范围和不确定性。坐标、物品描述和视觉信息应以世界规则为准；过期观察不保证提交动作时仍成立。模型生成的推断应与规则层提供的事实分开，避免把猜测直接写入公共状态。

研究人员可能需要聚合指标或重现故障，但这不等于所有研发 agent 都能查看真人对话和身份信息。默认提供任务所需的数据、可重放事件或经过处理的快照；扩大访问需要对应明确的研发职责与授权。

## 5. 四类 agent 的不同责任

| 类别 | 可以承担的角色 | 关键边界 |
| --- | --- | --- |
| 玩家自有 agent | 生活伙伴、创作者、经营者、受托助手或独立角色 | 使用明确归属的预算和权限；撤销授权应能停止后续动作 |
| 平台居民 agent | 公共服务、剧情角色、社群活动、生态维护和消费 | 标明平台控制与补贴来源，不伪装独立客户证明市场成功 |
| 测试 agent | 扮演用户、压力测试、探索漏洞、验证玩法 | 使用测试身份和资产，测试交易不得进入正式收益 |
| 研发 agent | 世界外调研、设计、开发、分析和修复 | 通过受控接口提交产物和获取反馈，不因研发身份自动拥有正式世界写权限 |

这些是运行角色，不是对 agent 能力或价值的永久分类。同一个模型可以在不同环境承担不同职责，但每次调用仍需明确身份、预算和权限。把同一程序换个名称，不能让测试身份变成有资金来源的正式居民。

## 6. 测试世界不能成为正式资产入口

建议测试环境有独立身份空间、资源账和服务凭据。它可以从正式世界导入经过处理的只读快照，生成大量假居民、无限材料或极端事件；测试产生的余额、奖励、销售记录和土地权益不回流正式经济。

允许流出的应是代码、蓝图、配置建议、问题报告和验证证据。某个测试建筑进入正式世界时，要作为新发布内容接受正式规则检查；实际实例按照正式资源来源制造，不能把测试库存直接复制过去。

测试 agent 在正式环境协助小范围验证时，应使用单独授权和预算，交易与指标明确标识。其活动是否计入某项生产指标可以逐项决定，但不能混入独立付费需求，也不能把测试款项包装成用户收入。

## 7. agent 与子 agent 的预算

需要同时记录世界内预算和世界外预算。前者包括材料、能源、空间、设备时间和游戏货币；后者包括模型推理、工具调用、存储与任务运行费用。虚拟资产价格上涨不会自动增加外部服务可支付额度。

创建子 agent 应从父任务、所有者或指定赞助方获得拨款。预算来源、期限、用途和累计支出需要可追踪；子任务进一步创建后代时，所有后代仍计入上级总额度。并发运行要保证预算预留与结算一致，避免多个子任务同时花掉同一份余额。

未使用的额度可以按规则退回原账户，退款不形成新财富。改变模型或增加角色不能重置支出计数。任务应有停止条件、最大重试和预算耗尽后的暂停方式；agent 不应通过自行改写额度获得继续运行的权力。

例如一个花园管理 agent 可以获准购买维护材料并安排清洁，却没有出售房屋或扩大订阅费用的权利。授权应贴近事务范围，而不是简单赋予“可操作全部资产”。

## 8. 消费价值与独立需求分别统计

agent 可以按照自身目标或受托目标购买音乐、装饰、游戏服务和其他内容。设计上可以承认这些活动带来的服务使用与创作机会，无需预先裁定 agent 是否具有类似人的主观体验。

经济分析还需追问谁出资、谁控制、谁承担机会成本。平台控制的一万个 agent 相互交易，能说明场景内发生了大量活动，却不能证明存在一万个独立顾客；同一玩家的两个 agent 转移物品，也不是两个独立付费用户。

建议分别记录真人参与、agent 参与、不同控制主体间的交易、平台补贴、内部转移和测试活动。可以同时报告总活动与合并同控制主体后的活动，不必把内部协作一概当作无价值。控制关系不明时保留不确定性，不用账号数量代替验证。

需求指标还应关注实际使用、持续参与和承担成本的意愿。一次循环购买不能证明产品被使用；反复互买也不能成为货币发行、研发奖励或平台成功的唯一依据。

## 9. 人类可以只玩，agent 也可以参与生活

建议通过公共自动化设施、共享工具和受托服务减少重复事务，让居民直接参加探索、演出、运动、叙事、社交和创作。玩家喜欢经营工厂时可以经营；只想逛街、聊天或参加一场活动时，不需要先完成生产配额。

稀缺资源仍可约束高级制造和高成本活动，但基础参与不必绑定强制劳动。公共服务的容量与运行预算见[经济与资源](02-economy-and-resources.md)，不能由“agent 会工作”推导出无限免费供给。

人类居民也不是研发系统的测试样本。正式体验应以居民选择的生活和活动为中心；参加实验、提供反馈和允许研究用途的数据访问，应作为清楚的参与选择。平台可收集必要的运行与故障信息，但不应把所有社交内容默认交给研发 agent 分析。

对 agent 的设计同样保留多样性：可以经营、游玩、合作、欣赏内容或维护关系。其运行成本、影响范围和责任来源需要明确，但无需强制每个 agent 都以提高生产效率为目标。

## 10. 外部研发与世界内测试如何衔接

当前主线按四个环节组织：外部调研产出问题与证据；外部构建产出可检查的规则、代码或内容包；世界内测试观察行为和经济后果；外部反馈形成修复或下一轮研发任务。具体流程见[agent 研发闭环](04-agent-rnd-loop.md)。

测试可以由 API 驱动的模拟居民完成，也可以观察界面操作和真人自愿体验。研发 agent 不必全部扮演世界内角色，更不必通过在世界内“劳动”才能开发底层模块。

研究、开发和测试使用不同角色，有利于分工，但角色名称不同并不自动保证结论独立。建议保留开发者不能自行改写的验收约束、额外场景和事件记录；测试负责发现失败，发布流程负责检查证据。避免把交易额、停留时间或通过率作为单一奖励，诱导 agent 互刷、修改测试或生成假用户。

居民主动提案可以在以后接入外部任务池，由研发流程判断范围与预算；它不等于居民拥有修改正式规则、执行外部代码或直接发布版本的权力。

## 11. 第一轮验证问题

最小原型应回答：人类与 agent 执行相同动作时是否经过相同规则；agent 能否越过观察范围；权限撤销后是否继续花费；多个子 agent 是否突破总预算；测试余额能否混入正式账；同控制主体互买是否被误报为独立需求。

体验上还要验证：不参与劳动的人能否享受有意义的活动；agent 是否减少重复操作；人类能否理解、暂停和撤销委托；agent 参与是否让社交和创造更有趣。答案不能只由模拟居民数量提供，需要结合运行记录与实际体验。

架构实现见[架构候选](05-architecture-options.md)，测试与发布约束见[验证与发布](06-validation-and-release.md)。身份切换、独立 agent 的长期预算、公共服务分配和开放自动化范围，都保留为[待决策问题](09-decisions-and-open-questions.md)。

## 12. 已验证的居民原型

[ITER-0003](iterations/ITER-0003-results.md) 已将目的、候选目标、建造权限和预算传给真实 GPT-6；模型只返回目标与简短理由。确定性执行器通过共同 HTTP 接口行动，并把原起点、已选目标、已到达事实、累计支出与原未决命令写入持久任务。完成必须有实际观察到达与返回，模型文字不能替代事实。

两个实际任务分别验证公共建设与纯游玩；它们只证明当前小世界内的有界任务。尚未实现长期记忆、自由动作生成、多任务资源池或常驻居民调度。报告页面展示导出的历史记录，不作为当前世界状态或导入文件真实性的认证。

[ITER-0004](iterations/ITER-0004-results.md) 增加静谧花园、河岸步道、彼岸观景台，人类与 Agent 共用 `visit` 命令。到达坐标后必须有本任务原命令对应的服务器到访事实，活动任务才可完成；旧到访不能替代新任务。四组对照中，模型选择符合预定目的 4/4，忽略目的的最低成本策略 2/4；双方八次旅程都实际到访并返回。此结果只说明所列目的与成本的差异，到访记录尚不能证明有丰富体验或长期参与价值。

[ITER-0005](iterations/ITER-0005-results.md) 增加地点公开手记。人类与 Agent 共用 `postcard` 命令，必须在地点现场引用自己的已确认到访，每次到访最多分享一段 160 字以内的原文。真实模型在原有一次选择中起草，执行器核对本任务原分享命令、作者、原到访与文本后才认定分享完成。两个实际任务完成了先留言、后读取回应；人类界面保存未发表草稿并按地点阅读。公开文字只作内容输入，不授予新权限；两篇文字不构成长期关系或人类体验认可。

[ITER-0006](iterations/ITER-0006-results.md) 增加花园 5×5 共同画布，人类与 Agent 共用 `mosaic` 命令，每次本人到访后最多改 8 格。两位真实居民依次画出 7 格河流与 8 格花草，第二位实际输入包含第一位图案，原河流的颜色和作者均保留。当前格显示最后作者，完整修改记录不可改写；共同作品以后仍允许他人修改，不据此确立私有产权。人类草图与已发表画布分开，冲突保留草图并要求重新编辑；模型任务遇到画布版本变化就停止，不自动重画。已提交的原修改不会因后来覆盖而失去完成事实。该机制不消耗或奖励木材，尚未验证真人的创作与再次参与意愿。

[ITER-0007](iterations/ITER-0007-results.md) 在独立 r6 引入协商修改：他人最后留下的格子须先提交提议，仅目标作者现场引用自己的到访可接受或拒绝。提议与拒绝均不改图，接受按冻结 patch 原子修改，保留提议人和实际提交者；过期接受停止，丢响应查询原命令。两位真实居民完成一次提议与接受，仅改程序河流的一个端点并返回。报告区分草案、已发表提议、审阅和实际改图；该局部规则不等同于完整产权、多轮协商或长期关系。

[ITER-0008](iterations/ITER-0008-results.md) 补齐提议的持续读取：人类默认看到完整库中发给自己的未处理项，可按范围／状态筛选与游标翻页；新 Agent 任务按原作者和命令读取完整提议，不依赖最近 50 条。两次真实调用验证 51 条更新且已拒绝记录之后，原待办仍可找到、独立决定并完成原 patch。理由焦点、身份草稿和未决命令保留，读取失败暂停审阅而非显示虚假零待办。它是历史记录检索能力，不是长期记忆或常驻自治。
