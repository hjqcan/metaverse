# 架构候选：支持世界演化的最小内核

> 状态：设计建议，尚未通过原型验证；首次整理于2026-10-25，2026-10-26补充文明状态与时间依据。
>
> 本文给出职责、接口和边界候选，不构成技术选型决定。尚未锁定 C#、游戏引擎、数据库、脚本运行时或区块链。

2026-10-25 更新：[底层研究](research/2026-10-25-foundation/00-report.md)将候选收敛为可执行的首轮建议，并验证了局部资源事务；本文其他架构能力仍需实际构建验证。

## 1. 架构要支持的目标

已明确的方向包括：世界从小规模开始，内容与规律可以逐步增长；人类与 Agent 都能入驻；参与者可以创造或游玩；经济不能允许任意增发物品。项目还希望探索由 Agent 分工完成调研、构建和入驻测试的研发循环。

架构不必第一天解决整个宇宙的并发规模，但应提前保留对象身份、资源语义、规则版本、观察权限和跨世界权益的边界。它们会影响后续内容的含义，迁移成本远高于更换某个界面组件。

建议初期采用**模块化单体**：一个可部署的核心服务内有明确的模块接口，先保证完整行为可验证。是否拆为独立服务，应由计算负载、故障隔离或团队协作的实际需求决定。

## 2. 候选模块与共同接口

| 模块 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| 身份与权限 | 角色、运营者、会话、授权及撤销 | 将所有 Agent 视为同一个后台账号 |
| 命令入口 | 接收意图、验证上下文、去重和排序 | 信任客户端自行提交的最终余额 |
| 世界状态 | 管理对象、区域、位置与生命周期 | 直接运行任意外来代码 |
| 资源与权益 | 记账、保留、转移、消耗和明确发行 | 根据物品名称推断资源来源 |
| 规则运行 | 执行获准规则、处理版本与依赖 | 绕过权限直接修改底层数据 |
| 观察与投影 | 为界面、Agent 和分析提供授权视图 | 默认向所有调用者返回完整世界 |
| 运行记录 | 保存动作结果、事件、快照和审计信息 | 把记录存在等同于行为一定正确 |

人类客户端与居民 Agent 使用共同的行动语义。前者可能通过图形界面发起“移动、建造、使用”；后者通过结构化 API 发起同类命令。不同角色可以拥有不同能力，但能力来自明确授权，不能来自接入方式的隐性特权。

## 3. 身份、对象与定义的候选模型

建议区分 `ActorId`、`OperatorId` 与 `SessionId`：居民身份、负责运行或管理它的主体、当前连接会话并非同一概念。Agent 重启或更换模型后，应能延续原身份；这不要求现在决定采用钱包、账号还是其他凭证。

对象侧可区分 `WorldId`、`RegionId`、`EntityId`、`DefinitionId`、`RuleSetId` 和 `RuleVersion`。这些名称只是接口草案，分别表达世界、规则区域、具体实例、设计定义及其规则依赖。

蓝图更新不能静默改写全部已售出或已使用的实例。实例需要知道自己依据哪个定义和规则版本产生；是否跟随升级，应由对象类型、区域政策及授权共同决定。更多语义见[世界与规则](01-world-and-rules.md)。

### 3.1 文明状态是分维度的派生视图

引擎能够表达某种对象，不等于居民已经制造并运营它。建议从权威账本、对象和事件中生成文明状态视图，按区域保留以下维度，而不设置一个自动递增的全局科技等级：

| 维度 | 需要表达的状态 |
| --- | --- |
| 知识 | 蓝图与工艺、证据、适用条件、许可和传播范围 |
| 设施 | 实际建成的设备、网络、位置、供应依赖与容量 |
| 可交付服务 | 能够提供的产品或服务、质量、队列，以及实际交付记录 |
| 可达性 | 不同居民的权限、价格、距离、等待和使用门槛 |
| 维护 | 设备状况、备件、操作与维护任务、供应连续性 |
| 社会与文化积累 | 组织与共享约定、作品、活动、署名和建设历史；按需要关联已有对象及事件 |

知道配方、能够生产、持续交付和普遍可用是不同事实。可承诺产能也不能替代已经交付的证据。世界最高科技、某个私人设施或一次成功演示，都不能直接代表所有地区和居民的生活水平。

时代称谓应由这些状态派生，供叙事和界面理解；它不应通过一次 `CivilizationLevel++` 自动授予建筑、资源或使用权。晚入身份读取当前世界及其实际可达服务，无须重置世界历史；基本教程与个人操作学习仍可独立存在。详见[文明演化](12-civilization-evolution.md)。

知识与规则扩展也应分开。LLM 可以提出配方或设计，获准规则负责检查其成立条件；若新设计超出现有引擎表达能力，需要经过研发与发布流程扩展规则，再由居民实际构建，不能用发布功能代替创造设施。

## 4. 权威状态与命令处理

“权威状态”表示有一个明确机制判断共享世界最终发生了什么，不预设它永远只能由一台服务器掌管。初期建议由核心服务裁决，以便集中验证；未来可以将不同区域交给不同运行者。

一个命令至少需要表达调用者、目标世界或区域、动作类型、参数、去重标识，以及适用时的预期状态版本。服务端应检查权限、对象存在性、资源、距离或时间条件，以及参数边界。

建议处理顺序为：接收命令、确认身份、读取相关状态、验证规则、原子提交变更、记录结果、更新观察视图。失败不得产生一半扣料、一半交付的状态；重复请求应返回既有结果或明确冲突，不能再次发货。

Roblox 官方安全文档要求服务端验证客户端输入，并特别关注货币、物品和用户生成内容的数值与权限边界。这是可借鉴的原则，不意味着采用 Roblox 技术栈。[R04](10-references.md#r04)

## 5. 资源账本与世界状态协同

资源数量、角色权益和物体位置需要保持一致。制造任务应明确区分已保留材料、已消耗材料、在制品和已交付成品，避免取消、断线和重试带来复制或丢失。

交易应同时描述各方变更；新增资源必须声明发行或储备来源。数量的表示方式要有明确精度和舍入规则，不能依赖任意浮点误差来维护稀缺性。具体采用整数单位、定点数或其他形式，应在原型中选择并验证。

本地事务是初期候选。跨服务或跨区域后，可以研究保留资源、确认转移和失败恢复等协议，但不应在没有对应需求时提前引入分布式事务复杂度。无论实现方式如何，同一公共权益不能在两处同时生效。

## 6. 事件、快照与可恢复性

建议同时保留当前状态、关键事件和周期快照。第一版不必采用完整事件溯源：只要能够解释关键变更、恢复故障并复现待调查行为即可。

事件应记录已接受的动作、适用规则版本、关键输入、时间依据和已确定结果。外部 AI 的输出、随机结果与外部服务决策，凡是影响状态的部分，都应在执行边界记录。

**回放时重放已记录的动作或结果，不重新调用 LLM“再想一次”。** 重新调用模型可能产生不同计划，也会消耗额外预算。若使用随机种子重建过程，还必须固定相关算法与版本；跨环境无法保证时，应记录已经裁决的结果。

快照需要关联事件位置和规则版本，恢复后校验账本与对象状态的一致性。事件日志本身不能阻止维护者篡改，也不能证明规则没有漏洞；若未来需要外部可验证性，必须另行定义签名、承诺或链上校验的信任模型。

## 7. 实时互动与慢速模拟分开

移动、碰撞和即时交互需要及时反馈，可以采用固定步长模拟、预测及纠正。制造、生态、建筑维护和部分经济活动则适合事件调度或较低频率结算。

二者通过明确的状态接口衔接。例如角色靠近机器的实时状态影响是否可以操作，制造任务本身可以在较慢的调度器中推进。不能为了远处一片森林持续更新，就让所有树木每帧执行昂贵逻辑。

后台运行和离线结算必须遵守相同规则。“离线时长乘产量”只有在材料、能源、容量和权限始终满足条件时才成立。

例如，每件工具耗 2 单位金属、3 单位能源，需 5 分钟。任务有 10 单位金属、9 单位能源，成品仓只剩 2 个位置，离线 60 分钟。可完成数量为 `min(12, 5, 3, 2) = 2`：消耗 4 单位金属和 6 单位能源后因满仓停止，而不是产生 12 件工具。

这个例子假定条件固定且仓位独立。存在共享电网、其他任务或中途运输时，需要推进到下一次条件变化，再重新计算。结算所用时间由权威运行机制确定，不能接受客户端自行申报离线时长。

### 7.1 区分三种时间依据

| 时间依据 | 记录内容 | 与文明能力的关系 |
| --- | --- | --- |
| 现实时间与预算 | 推理、执行、存储、费用和运行时长 | 约束系统可承担的研究与运营成本，不直接兑换世界产物 |
| 权威模拟时间 | 生产、运输、生态与维护按哪些规则推进 | 决定合法任务的完成与中断；加速、暂停和离线推进需有明示规则 |
| 能力进度 | 知识、设施、服务、可达性和维护状态的事件变化 | 不是钟表计时量；可能停滞、分化或局部回退 |

更多 Agent 或推理预算可以带来更多候选计划，但执行仍受材料、能源、设施容量与模拟时间限制。不能把现实过去一天、模型调用次数增加或引擎版本升级直接解释为文明进入下一时代。

没有居民下新指令时，已获准的任务可以继续运行；是否发生供应耗尽或维护退化，由规则决定。这与整个模拟暂停不同，实验记录必须区分。执行层的快速调节、生产维护的中速排程、研究与制度的慢速反馈，也不应混成同一个更新频率。

## 8. 规则接口与脚本运行候选

规则模块可声明观察需求、可接受动作、验证逻辑、状态变更、时间推进和版本迁移。名称可以暂用 `Observe`、`Validate`、`Apply`、`Advance`、`Migrate`，但职责分离比最终命名重要。

验证后到提交前，还需检查相关状态是否已经变化，避免两个请求同时花掉同一份材料。模块产生的变更仍通过核心权限与账本接口提交；它不能因为通过了初次审核就获得无限写权限。

| 扩展方式 | 适用方向 | 主要取舍 |
| --- | --- | --- |
| 声明式配方与组件 | 常见内容、制作和基础行为组合 | 易检查，但表达能力有限 |
| 受限脚本或隔离运行时 | 新动作、新局部状态和玩法 | 更灵活，需要执行与权限约束 |
| 受信任的原生模块 | 内核能力、性能敏感逻辑 | 权限大，发布与验证要求更高 |

无论采用哪种运行时，都要限制可访问对象、外部网络、执行时间、内存、递归或任务数量，以及资源写入范围。运行在某种字节码环境中，并不自动保证安全；宿主接口若暴露无限权限，隔离也失去意义。

## 9. Agent 运行与研发环境的边界

居民 Agent 的推理服务可以位于世界运行时之外，通过观察和行动接口参与世界。记忆、模型和计划器不应直接获取数据库管理权限。世界内资源与现实推理费用分别记账，虚拟能源不会自动支付服务器和模型账单。

研发主循环由世界外的调研、构建、验证和发布角色承担。居民 Agent 的行为可以成为测试与观察材料，但不要求每位居民主动研究系统，也不将其设为主要研发组织方式。详见[Agent 研发循环](04-agent-rnd-loop.md)。

开发凭证、测试凭证与居民凭证应分离。候选规则在独立副本中运行，副本资源不能返回正式公共账本。评估完成后发布的是规则或作品定义，以及明确的迁移方案，而不是把测试产生的财富直接合并回去。

## 10. 为未来链上能力预留信任边界

采用区块链不是当前选型决定。但若未来考虑它，需要提前区分世界运行状态、可转移权益和外部结算，避免把“链上拥有凭证”误作“链上验证了全部世界行为”。

至少需要回答：谁有权声明链下制造完成；哪些状态由链验证；规则升级谁批准；链下回滚与链上已确认转移发生冲突时怎么办；跨世界转移由谁托管或验证；凭证持有人实际获得什么使用能力。

MUD 的 World 架构可以作为链上世界组织方式的研究入口，但它不是本项目已经采用的框架，也不替代上述信任与经济设计。[R05](10-references.md#r05)

## 11. 最先验证什么

第一轮不以服务数量和技术栈复杂度作为进度指标。建议验证同一套接口能否支持人类与 Agent 行动；重复命令是否只生效一次；资源不足时是否完整失败；离线结算是否正确停止；规则升级是否识别旧实例；副本与正式世界是否隔离。

同时验证跨区制作与拆解能否检测资源增发，以及记录能否在不重调 LLM 的情况下解释一次事故。只有出现具体性能或隔离瓶颈后，再决定拆分服务、增加并行模拟或引入新基础设施。验收安排见[验证与发布](06-validation-and-release.md)，未决技术与治理选择见[决策与开放问题](09-decisions-and-open-questions.md)。
