# 验证、证据与发布

> 首次整理：2026-10-25；更新：2026-10-26。状态：设计建议，尚未通过本项目的实现与实验验证。本文定义准备建立的验证制度，不表示已经存在可自主研发、入驻或发布的完整系统。

## 1. 验证服务于什么目标

本项目允许人类与 Agent 共同居住。人类可以创造、协作，也可以不承担生产劳动而享受世界；不能把人类劳动时长或持续在线当作经济成立的前提。Agent 的研发能力、居民行为与运营成本，都需要被验证。

验证的核心问题是：**一次修改是否让世界更可靠、更符合既定方向，而且证据足以支持发布？** 自动完成任务、通过编译、获得较高自评分，只能回答其中一部分。

相关研究为自然语言驱动的社会模拟、程序技能积累、环境交互和代码改进提供了参考，但研究环境中的结果不能直接证明本项目能够长期自治运行。参见 [R10](10-references.md#r10)、[R11](10-references.md#r11)、[R12](10-references.md#r12)、[R13](10-references.md#r13)。

## 2. 建立两条反馈回路

两条回路共享“外部调研—提出假设—制定方案”的入口，但提供不同证据。

| 回路 | 主要观测 | 反馈去向 |
| --- | --- | --- |
| 构建反馈 | 功能正确性、资源账本、权限、性能、成本、迁移兼容性 | 明确的实现缺陷进入局部修复；反复失败或规格矛盾返回研究与方案设计 |
| 入驻活动反馈 | 合作与交易、资源分配、长期演化、策略支配、居民可达目标 | 调整待检验的机制假设；必要时重新定义实验与验收标准 |

例如，制作操作重复扣款属于实现缺陷；合法操作组合持续产生无限套利，可能是配方、市场或制度假设有误。两者都不能靠让测试 Agent “更配合”来解决。

完整研发关系见 [Agent 研发闭环](04-agent-rnd-loop.md)。反馈可以触发新一轮调研；研究结论必须再经过实验，不能直接成为世界规则。

## 3. 先规定证据，再生成候选实现

一次候选修改应按以下顺序推进：

1. 写清问题、目标、非目标与可能失败的原因。
2. 确定验收条件、固定参考测试及独立保留场景。
3. 冻结本轮规则版本、初始条件与资源预算。
4. 在隔离分支和世界副本中实现候选方案。
5. 对照基线运行，记录成功、失败和成本。
6. 根据预设发布条件接受、撤销或返回研究。

验收条件不能由实现者在失败后静默放宽。如果发现原规格错误，可以修改规格，但必须生成新版本，记录理由，并重新评价基线与候选。保留场景一旦被反复用于指导修改，便逐渐成为开发数据，需要轮换和补充。

## 4. 三层判断，三种证据

| 层次 | 典型问题 | 合适证据 |
| --- | --- | --- |
| 程序硬事实 | 是否重复消费？越权操作是否生效？资源是否出现非法来源？ | 权威账本、断言、事务检查、边界与并发测试、可重放操作序列 |
| 系统行为 | 是否形成支配策略？新人是否被排除？生产链是否长期断裂？ | 多策略、多场景、长短周期的对照实验与分布数据 |
| 设计判断 | 新功能是否符合世界方向？体验是否值得保留？ | 可观察行为、明确设计目标、外部体验反馈与有依据的评审 |

LLM 可以归纳证据和提出解释，不能代替账本证明，也不能只靠自己的打分宣布机制成功。应区分“未观察到失败”“在给定条件下满足要求”和“已证明某项不变量”；三者可信范围不同。

## 5. 居民测试必须具有策略差异

至少维护三类居民：

- **固定参考居民：**冻结策略、工具权限和预算，比较世界版本；简单规则程序也能成为有用基线。
- **自适应居民：**允许积累经验或调整策略，观察世界在学习压力下的演化。
- **对抗居民：**在隔离环境内主动寻找套利、死锁、资源复制和权限漏洞。

每类还应改变目标、能力、预算、信息与时间尺度。例如，合作建设与独占利润、初学者与专家、局部观测与完整观测、短期收益与长期经营，都可能暴露不同问题。

不同模型、不同角色提示词不必然意味着独立证据。若它们共享资料、工具、奖励和错误假设，结论仍可能高度相关。增加相似居民数量不能替代扩大行为覆盖。

居民应通过正常世界接口行动；特权观察器用于记录与判定，不应暗中帮助居民完成任务。测试账户、资产与市场必须隔离，测试居民的活动也不能计作真实用户需求。

## 6. 用矩阵识别共同适应

测试单位应是：**世界版本 × 居民策略 × 场景**。设评价函数为：

$$
J(\theta,\phi,\xi)
$$

其中，$\theta$ 是世界规则，$\phi$ 是居民策略，$\xi$ 是初态、任务与扰动。若三者同时变化，分数上升的原因就无法明确归因。

因此，新旧世界首先应在固定居民与成对初态上比较，再检验自适应居民和对抗居民。结果应保留各类型的失败率、成本及差异，不能只汇总成一个总分。场景需覆盖资源紧缺、参与者增长或离开、物流中断和恶意操作等具体假设。

统计结论要说明样本条件与相关性；重复相同轨迹的成功不能当作大量独立成功。自动系统应能报告“不确定，需要新实验”，而非被要求每轮都给出可发布结论。

指标也要防止被优化过程误用。交易次数增加可能来自居民互相倒卖，在线时长增加可能来自任务阻塞，产量上升可能以维护费用失控为代价。每项主要指标应有对应的反例检查，并同时记录资源与真实计算成本。人类不参加劳动或暂时离开，不应被自动判为居民失败。

### 6.1 文明演化需要能力与身份的对照

文明实验应在同一规则版本下记录早期到后期的实际轨迹，分别测量知识、设施、服务交付、可达性与维护状态。还需按区域、早期居民和晚入身份分组；全球最高科技或老居民的平均能力，不能替代新居民真正取得服务的证据。

| 需要区分的事实 | 应保留的证据 |
| --- | --- |
| 声称掌握与经过验证 | 设计来源、验证条件、实验结果与适用规则 |
| 建成与能够运行 | 材料去向、设施实例、供应、操作与维护条件 |
| 理论产能与实际服务 | 请求、队列、执行、交付、质量与失败原因 |
| 世界存在与居民可用 | 身份、权限、价格、等待、地点与必要劳动 |
| 能力扩大与代价增加 | 资源占用、现实预算、依赖与恢复条件 |

建议先比较“没有建设共享设施”与“居民实际建设并运行设施”两组，再加入停供、维护变化和 Agent 预算变化。对照初态、模拟时长与居民任务应提前规定；指标阈值在运行前确定。

文明快照应关联产生它的动作轨迹。直接注入成熟设施可以用于独立的容量或故障测试，但必须标注为人工测试初态，不能宣称该测试已经证明文明由居民演化。测试运行中增加规则或改变验收器，也应另起版本，避免归因混乱。

更多 Agent 不必然更快，推理预算提高也不保证服务改善；瓶颈、资源竞争和计划差异都可能改变结果。停滞、局部退化或无改善可以是有效发现。验收关注因果可解释、能力可兑现和约束被遵守，不要求每次实验都呈现正向发展。模型范围见[文明演化](12-civilization-evolution.md)。

### 6.2 先发优势与入口封锁分别验证

用户已确认先发优势应适度、不得形成垄断。实验要分别测量早入与晚入居民在同类目标下的有效能力差距，以及资源、技术、设备、场地和通道是否被单一主体或关联集团封锁。没有单一大户不等于差距合理，有公共消费服务也不等于新人能够继续创造。

在既有共享工坊场景中，可让主要供应者拒绝服务、提高费用、占满容量或控制多个表面独立入口。让新人实际完成一条替代路径，记录材料、价格、时间、品质和公共预算，而不是由模型口头判断替代存在。早期只有第一家设施不自动判失败；需要考察服务条件、形成替代所需投入及其期限。

长期场景应加入不同批次、离线返回、同主体分身和新区域再次被控制。门槛提前约定，未识别的共同控制与未覆盖的策略如实记录。测试不能通过临时补发材料、强制劳动或删除合法历史来获得通过结果。候选指标及副作用见[专题](13-entry-and-bounded-advantage.md)。

## 7. 最小证据包

每轮实验至少记录下列内容，并以实验 ID 关联：

| 类别 | 内容 |
| --- | --- |
| 版本 | 代码提交、世界规则、配方、接口、验收器与场景版本 |
| 起点 | 世界快照、初始账本、任务、环境条件与可控随机种子 |
| 居民 | 模型标识、配置、策略、工具权限、预算、记忆与检查点引用 |
| 轨迹 | 实际动作、工具结果、状态变化、关键事件与拒绝原因 |
| 成本 | 推理调用、计算量、运行时间、失败重试与外部费用 |
| 结论 | 指标、失败复现、与基线的差异、局限和发布决定 |

LLM 调用不能仅靠 seed 保证复现。应保存必要的输入、输出及实际动作，使用动作重放验证世界状态变化；若重新生成动作，应将其视作新的行为实验。敏感凭据不进入证据包，居民内部不可观测的推理也不作为验证依赖。

## 8. 自动发布建立在明确授权范围内

不要求每次小改动都由人类逐步批准。可以预先配置自动发布策略：允许修改哪些模块、最大预算和影响范围、必须满足哪些验收条件、遇到什么情况停止或撤销。

在已授予的权限和预算内，系统可以自动修复、验证并发布。规则根本变化等是否允许自动发布，应在策略中事先明确；超预算或既有授权未覆盖的操作，应提交具体变更与证据，进入相应审批流程。Agent 不能通过修改验收器或自己的权限来获得发布资格。

运行策略还应包含停止条件：达到成本或时间上限、连续尝试没有新增证据、关键不变量被破坏、监测与账本相互矛盾。停止后保留现场，说明已知事实和剩余疑问。能够及时停止无效搜索，是自动系统的一项能力，不应通过无上限重试掩盖失败。

**本文描述的是待配置的制度，不构成对未来无限部署、现网改写或外部资金操作的授权。** 本轮文档工作也不表示这些能力已部署。

## 9. 发布、迁移与回撤

候选方案应先进入隔离世界，再按预定影响范围渐进启用。发布前检查旧物品、配方、合约、居民脚本与接口的兼容性；迁移需要可识别的版本、可重试规则和执行记录。

回撤应区分代码与状态。隔离实验可以恢复快照；已有居民的持久世界不能把“恢复旧快照”当作通用答案，因为这可能抹掉发布后有效交易与创造。

应优先保留有效交易，暂停受影响入口，再以修复逻辑、兼容读取或有记录的补偿迁移处理状态。若确实需要撤销非法交易，应依据事先定义的规则识别影响范围，保留审计链，而不是静默改余额。具体策略取决于架构，参见 [架构选项](05-architecture-options.md)。

## 10. 首次验证从一个完整过程开始

基础验证可围绕“取得资源—制作物品—转移所有权—持续使用”建立最小证据链，同时加入资源不足、重复请求、进程中断和越权操作。居民数量、时间尺度和阈值由实验目标确定，不预先伪造精度。

为贴近共享文明的愿景，路线文档新增 `EXP-0002`“从手工建造到共享工坊”，推荐作为首个产品实验候选：观察居民如何实际建成服务，再验证晚入身份能否直接使用。原 `EXP-0001` 两地通行保留为可选基础机制实验。编号与建议顺序的变化不代表任何实验已经运行。

截至本版，没有本项目的测试结果可以宣称通过。下一步应依 [首个实验](07-roadmap-and-first-experiment.md) 产生真实证据，并把未解决的假设写入 [决策与开放问题](09-decisions-and-open-questions.md)。
