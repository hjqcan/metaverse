# 路线与首个实验

首次整理：2026-10-25；更新：2026-10-26（Asia/Shanghai）。

状态：建议路线；阶段顺序、实验题材与阈值尚待提案确认。无工期、成本或性能承诺。

## 1. 以验证关口组织建设

用户希望长期、渐进地叠加底层。路线因此按“下一步要获得什么证据”组织，而不预先排出完整宇宙的交付日历。

世界扩展与研发闭环可以同时从很小的规模起步。少量 Agent 就能开展首轮测试；早期提到的 10—30 名真实玩家只是规模示例，不是启动条件，也不是当前承诺。

| 阶段 | 建设内容 | 进入下一阶段前要得到的证据 |
|---|---|---|
| A · 研究基线 | 明确愿景、状态、待决问题与提案格式 | 不同角色理解一致，能区分决定、建议和假设 |
| B · 最小世界 | 小片陆地、对象、基础资源、状态持久化、简单观察与动作 | 状态能推进并恢复，资源变更可追踪，Agent 能实际行动 |
| C · 首轮闭环 | 外部研究、候选实现、入驻测试、反馈与方案修订 | 至少完整运行一轮，形成有证据的采用、修订或拒绝决定，并保留成功与失败记录 |
| D · 共建能力 | 蓝图、组件、工具与工坊、行为编排、共享与许可 | 不同参与者能继续创造，晚入居民能实际使用已有服务，成本和权限清楚 |
| E · 世界扩展 | 新区域、新对象类型、新规律与局部版本 | 新能力可被采用，已有作品有兼容或迁移办法 |
| F · 长期运行 | 更丰富的活动、组织、公共服务、经济与多方运营 | 在居民变化、长期积累和规则升级中保持连续与可维护 |

阶段并不要求一次完成后永久封闭。新的证据可以使项目返回之前的阶段修改假设。

## 2. 第一轮应先决定什么

优先回答下列问题：

1. 最小世界有哪些对象与状态，什么变化需要记账？
2. Agent 能观察什么、提交什么动作、怎样知道失败原因？
3. 外部研究与构建怎样交换方案和问题？
4. 本轮实现的一个目标是什么，怎样验收？
5. 哪些已有状态必须保持连续，测试资产怎样隔离？

语言、引擎与数据库服务于这些问题。C# 等熟悉技术可以作为原型候选，不提前锁定最终平台。参考[架构候选](05-architecture-options.md)。

## 3. 推荐的首个产品实验候选：从手工建造到共享工坊

建议实验编号：`EXP-0002`。本次讨论进一步明确了“居民共同推动文明，晚入者面对当时世界”的方向，因此新增本提案，推荐为更贴近愿景的首个产品实验候选。原 `EXP-0001` 保留为可选基础机制实验；编号是提案标识，不是执行顺序或完成记录。**两个实验均尚未运行。**

### 3.1 研究问题

同一小世界能否从手工制作出发，经居民实际投入和建设形成可运行的共享工坊，并让后来的新身份直接使用已有服务？

要验证的是一条可追溯的能力形成过程，不是界面从“原始时代”切换到“工业时代”。世界不为每个新人重置历史，新人也不必重新解锁全部个人科技树。其权限、费用、基本操作学习和可能的必要条件，仍需在实验中明确。

### 3.2 初态与前置能力

初始世界包含小片可活动区域、有限且来源明确的材料、少量居民，以及一种基础构件的手工制作方式。构件具体是什么，留给提案确定；第一轮不需要真实冶金、完整能源系统或大规模市场。

需要逐步实现的前置能力包括：对象和库存持久化、合法制作与建造、设施任务与交付、身份与访问条件、运行记录，以及隔离副本。不能假定这些能力已经存在。

本轮允许表达哪些工具和工坊、哪些配方有效，应在运行前说明。LLM 可以提出方案，但不能仅凭文本宣布新资源或设施合法。如果候选方案要求引擎增加新规律，应先研究、验证并发布规则版本，再重新确定实验基线。

### 3.3 同一世界中的能力形成轨迹

| 阶段 | 居民实际活动 | 必须留下的证据 |
| --- | --- | --- |
| 手工起点 | 取得材料、执行基础制作，记录限制 | 初态、材料来源、动作、时间与成品 |
| 工具形成 | 制造合法工具，验证其在任务中的效果 | 配方条件、实际消耗、工具实例与使用记录 |
| 工坊建设 | 投入材料建成设施，建立供应、操作和任务流程 | 建造事件、设施状态、输入输出与运行条件 |
| 服务提供 | 接受需求，经实际运行交付构件或制作服务 | 请求、队列、执行者、消耗、交付与失败原因 |
| 晚入使用 | 新身份进入当前世界并请求已有服务 | 权限、费用、等待、必要劳动与最终取得的结果 |

工坊是否完全自动化是一个独立维度；早期也可以由居民 Agent 运营。晚入者能够使用他人成果，不要求早期工坊已经具备无人维护的能力。是否需要动力、操作人员或其他供应，依据选定规则检查，不能在离线结算时忽略。

成熟状态应由该世界中的建设与运行产生。不得直接生成一座成熟工坊，再将其使用成功描述为文明已经演化。人工注入设施可以另做独立的容量、权限或故障测试，但需要明确标注，并与演化证据分开。

### 3.4 无建设与有建设的两组对照

从同一初态建立隔离对照副本：

- **无建设组：**保留手工生产路线，不建设共享工坊。
- **有建设组：**允许居民用实际材料、时间和运行资源建设并运营工坊。

两组采用相同规则版本、初始预算、权威模拟时长与后入任务。建设引起的资源余量和基础设施差异是需要记录的结果，不应通过补发资源抹平。晚入身份的初始条件应相同，服务访问政策及可能的公共预算来源需提前说明。

比较重点是同一类需求能否被满足、谁承担生产和维护、晚入者承担多少操作与等待，以及世界总共付出了什么代价。工坊建设可能过早、成本过高或供应不足，因此不能把有建设组必然胜出设为验收条件。

### 3.5 各角色交付与反馈

研究组明确目标、可用机制、候选工坊、成本假设、验收条件和可能失败的原因。构建组实现必要接口，说明当前能力与限制。测试组使用固定参考、探索和对抗居民，覆盖基础任务、重复请求、输入不足、越权及中断恢复。

局部程序缺陷反馈给构建组；合法规则下始终无法形成可用服务，或者成本与需求假设不成立，则返回研究组修改方案。改变规则后重新建立对照，不能让测试居民暗中放宽要求。

### 3.6 指标与完成标准

| 维度 | 计划记录的指标 |
| --- | --- |
| 知识与构建 | 设计是否经检查、工具与设施是否实际建成、材料来源去向 |
| 运行能力 | 输入和维护条件、实际处理量、成功交付、停机与失败原因 |
| 早期居民 | 建设投入、操作与维护负担、获得的能力及权益 |
| 晚入居民 | 服务可达性、费用、等待、必要劳动、取得合格结果的情况 |
| 世界成本 | 材料、能源或其他运行资源、现实推理与执行预算 |
| 连续性 | 世界重启、后入身份创建和规则兼容时，已有状态是否延续 |

先定义测量口径和阈值，再运行实验。全球最高科技、总建筑数或 Agent 自评分不能替代分身份的实际交付证据。完成一轮闭环至少要有可检查的结果、明确的采用或拒绝理由，以及需要修订时对修订结果的复核；没有改善也可以形成有效结论。

### 3.7 后续扩展场景

先完成基础对照，再按需要加入：

- **供应或维护变化：**停止某项输入或维护，在模拟时间继续推进的条件下观察缓冲、停运、退化与恢复。是否退化及其速度以已声明规则为准。
- **Agent 预算变化：**固定世界资源与物理执行约束，改变推理预算或居民数量，观察计划、服务与成本。更多 Agent 不必然更快，遇到瓶颈而无改善不是自动失败。
- **人类活动变化：**比较人类持续操作与只消费服务的情况，检查哪些运营工作可由 Agent 承担，以及对应成本。
- **先行者拒绝合作：**让最早工坊及其关联供应者拒绝服务、提高费用或阻断通道，检查后来者是否能实际使用替代或独立建设，并记录全部代价。
- **长期差距与分身：**比较多批居民的当代参与、创作门槛及有效能力差距，检查同主体多个 Agent 能否占满公共额度和新入口。

这些场景帮助区分现实预算、权威模拟时间和能力进度，不能把经过更多时间或调用更多模型当作文明升级。模型与边界见[文明演化](12-civilization-evolution.md)。

新增的先发与垄断场景对应 C16、C17。公共制度和量化阈值仍需提案决定，实验尚未运行；具体观察方法见[先发优势与后来者机会](13-entry-and-bounded-advantage.md)。

## 4. 可选基础机制实验：连接两块小地块

建议实验编号：`EXP-0001`。这是此前提出的候选，现保留用于通行、资源和研发反馈等基础机制验证；可以根据前置能力需要先开展。它并未因提案编号较小而被视作已经完成。

### 4.1 研究问题

能否通过一次外部研究—构建—入驻测试—反馈迭代，让参与者从初始地块到达另一个可观察的地点，并保持资源核算和已有对象正常？

这个题材允许研究组比较桥梁、简化船只或其他机制，不预设必须先实现完整海洋、经济市场或真实流体。若当前世界连基本移动都未实现，应先把它作为前置实验。

### 4.2 前置能力

- 能表示小范围空间、居民和少量对象。
- 能提交移动或交互动作，返回明确结果。
- 能记录有限材料的领取、使用和回收来源。
- 能保存候选世界状态，创建隔离的测试副本。
- 外部团队能读取文档、代码和实验记录。

这些能力也要逐步实现，不能在提案中假设已经存在。

### 4.3 研究组交付

写出需求解释、两个或以上有实际区别的候选方案、选取理由、必要状态、资源成本和验收条件。若只有一个合理方案，也应说明为何无需制造虚假备选项。

验收指标区分：必须满足的正确性约束、计划测量的行为指标、仅用于探索的开放问题。阈值在运行前约定，不能看到结果后偷偷修改。

### 4.4 构建组交付

提供可运行版本、实际使用的技术与接口、已完成和未完成的范围，以及实现障碍。涉及状态格式或资源规则的变动，说明对原有对象的影响。

如果成本或能力不支持原方案，给研究组可复现证据和替代选项；不要仅为达到字面目标而移除资源约束。

### 4.5 测试组活动

固定参考居民完成基本往返；探索居民尝试不同路线与组合；对抗居民尝试重复命令、反复搬运、断线恢复及制造—拆解边界。

测试既可以通过原生接口，也需要覆盖实际客户端相关路径。无画面规则测试不能替代对图形、输入或实时交互缺陷的检查。

### 4.6 候选验收内容

| 检查 | 需要记录的证据 |
|---|---|
| 通行能力 | 任务、初始条件、实际轨迹、成功与失败原因 |
| 资源正确性 | 变更前后数量、来源去向、重复动作处理 |
| 连续性 | 重启或恢复后的对象、位置与任务状态 |
| 兼容性 | 原有对象与基础操作是否仍成立 |
| 成本 | 推理、执行、存储与实际运行时间 |
| 新用途 | 是否出现候选方案未预想到的有效组合 |

记录结果时使用“未运行、通过、失败、证据不足、不适用”等准确状态。当前文档没有任何实际通过率。

### 4.7 完成标准

首轮闭环的完成，至少包括一次可检查的反馈、一项有理由的方案或实现修订，以及对修订结果的复核。若实验没有改善，也应明确拒绝或暂停原因；诚实的否定结果仍能减少后续不确定性。

## 5. 后续可研究的能力

| 能力 | 可能的新活动 | 依赖或主要疑问 |
|---|---|---|
| 水体、浮力与航行 | 船、港口、浮动建筑、竞赛 | 精度、成本、对象与资源边界 |
| 可编程工具与机器 | 自动建造、运输、艺术装置 | 脚本权限、运行额度与行为组合 |
| 生长与生态 | 园林、种植、物种设计 | 再生来源、长期稳定与可解释性 |
| 星空与其他地区 | 观测、航行、异星社区 | 背景到可进入地点的迁移、区域规则 |
| 天堂与地下世界 | 新的生命状态、文化与探索 | 身份连续性、当地规则与物品转换 |
| 创作与活动空间 | 展览、音乐、表演、小游戏 | 创作工具、运行预算与公共服务 |

该表是研究方向，不是固定解锁顺序。普通玩家能否直接创造新规则，对应 Q02，必须另行明确。

## 6. 经济与系统压力实验

在基础活动成立后，逐步加入下列情景；不必把全部实验塞进第一版：

- 停止新增居民与外部资金，已有活动是否仍有意义。
- 自动化效率显著提高，库存、价格和活动选择怎样变化。
- 大量居民暂时离开或回归，资源与公共设施如何响应。
- 新地区采用不同拆解规则，跨区循环是否凭空增发。
- 一组 Agent 控制多个身份，能否绕过预算或补贴约束。
- 规则升级、维护停止或场景分支，已有作品怎样延续。

这些都是测试设计，不是对任何经济机制有效性的保证。

## 7. 当前建议后置的事项

全链运行、代币与真实货币兑换、大规模并发、完整真实物理、无约束规则生成和基础模型训练，都需要明确问题与证据后再决定。

基础身份、资源来源、规则作用范围、版本与反馈格式则应较早明确，因为它们会影响所有后续能力。

## 8. 阶段结束时的交接

每个阶段至少留下：实际版本、变化说明、证据位置、成本、失败路线、尚未验证的结论，以及更新后的待决问题。使用[反馈报告模板](templates/feedback-report.md)，并同步修订[决定记录](09-decisions-and-open-questions.md)。

项目的近期开端是一个很小但可以被改进的世界，以及一条能据实迭代的研发流程。规模随着这些能力的证据增长。
