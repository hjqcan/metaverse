# 决定、建议与待决问题

首次整理：2026-10-25；更新：2026-10-26（Asia/Shanghai）。

状态：持续更新的讨论基线。此文件区分用户已经表达的方向与尚待采用的设计建议。

## 1. 状态约定

| 标记 | 含义 |
|---|---|
| C · 已确认 | 用户在本次讨论中明确提出或澄清的方向 |
| P · 设计建议 | 助手提出、整理进入文档，但未被逐项确认的方案 |
| E · 可选补充 | 讨论过并保留的扩展方向，不构成当前必做范围 |
| Q · 待决 | 会影响具体方案，尚需研究、实验或明确选择的问题 |
| X · 已修正或排除 | 早期解释已被后续澄清限制，或新讨论明确排除的误读 |

“已确认”描述需求来源，不代表相关软件已经实现。“设计建议”被写入仓库，不自动转换为已批准的实施计划。

## 3. 尚未逐项采纳的主要建议

| 编号 | 设计建议 | 目的与需要验证的条件 |
|---|---|---|
| P01 | 元规则、具体规则、内容分层 | 支持规则增加；需要验证作用范围、冲突与版本关系 |
| P02 | 将蓝图或设计与正式世界实例分开 | 兼顾创作自由与制造成本；许可和功能计价仍待设计 |
| P03 | 不同区域可采用不同规则，跨区明确转换 | 支持奇幻和异星世界；需要核算边界与可理解的转换行为 |
| P04 | 权威状态、事务化资源账、可追溯变更 | 防止重复发货与不完整交易；具体实现待选型 |
| P05 | 固定参考、自适应、对抗 Agent 联合测试 | 识别规则变化、策略变化和利用方式；需要代表性场景 |
| P06 | 先验证小世界及一轮完整研发迭代 | 以证据发现协作缺口；机制和阈值需要提案确定 |
| P07 | 核心规则支持无画面运行，保留实际客户端测试 | 降低部分实验成本；不得用简化替身冒充实际系统验证 |
| P08 | 新规则先在隔离副本或地区试验，再按版本采用 | 保留世界连续性；需要迁移和兼容策略 |
| P09 | 研究公共设施与基础服务供给 | 支持不劳动也可游玩；不承诺无限免费算力与资源 |
| P10 | 设计独立验收、授权边界和预算内自动迭代 | 减少逐项人工介入；本次文档提交不等于授权未来无限运行 |
| P11 | 以 C# 等熟悉技术构建候选内核 | 降低起步成本；引擎、语言、数据库都未正式选定 |
| P12 | 按地区记录文明能力分布，时代称谓从实际状态推导 | 区分知识、设施、服务、可达性、维护及社会文化积累；全球与地区口径待定 |
| P13 | 以可验证设计、合法建造、持续运行与传播记录技术形成 | 支持在既有规律内组合发明；新增基础能力继续通过外部研发闭环 |
| P14 | 按当代实际服务提供入驻引导，研究共享知识、工坊和基础供给 | 让后来者受益并继续创造；产权、资金、容量和分配方式待选择 |
| P15 | 分开现实计算预算、权威模拟时间与文明能力变化 | 允许 Agent 加速探索和协作，实际产出仍由材料、能源、设施等约束 |
| P16 | 以 EXP-0002 手工建造到共享工坊作为首个产品实验候选 | 同一持续世界中形成设施，再由后入居民实际使用；EXP-0001 保留为可选基础机制实验，两者均未运行 |
| P17 | 分开知识保留、设施维护和服务退化，保留可追溯历史 | 支持停运与恢复；不默认靠周期清档更新玩法，具体生命周期仍待确认 |
| P18 | 分开历史价值、有限功能收益与排他权，研究可追赶的基础能力和多样成长 | 落实适度先发；不把取消全部财富差异或抹去经验当作目标 |
| P19 | 用可实际取得的公共或竞争性替代，保持资源、技术、场地和服务入口开放 | 供给有成本有来源，控制关系按证据记录，不能仅用商店数量证明竞争 |
| P20 | 在共享工坊实验中加入拒绝服务、关联控制、独立创作与长期差距测试 | 验证消费者和创作者两种机会，不要求所有早期服务立刻有多家供应者 |

## 4. 可选补充

- **E01：世界内居民主动提案。** 用户认为这是有价值的补充；当前主线仍是外部研发团队。它可以增加需求来源，不能替换 C10—C11。
- **E02：改进研发系统本身。** 研究 Agent 可提出工具、记忆、任务拆分、评测方式的改进。需要独立验证，不等同于基础模型自行训练。
- **E03：合作聚落与可编程机器人。** 早期提出的特色题材，可用于验证系统组合，不限定整个产品。

## 5. 待决问题

| 编号 | 问题 | 为什么重要 | 建议如何获得答案 |
|---|---|---|---|
| Q01 | “轻度膨胀”的首要指标是什么？ | 决定资源入口、货币规则与监测目标 | 对比物资、人均产能、货币与基础价格的情景模拟 |
| Q02 | 哪些参与者能创建、提交、采用和升级规则？ | 决定创作接口、治理与发布权限 | 设计几种权限方案，并演练局部与全局变更 |
| Q03 | 哪些资源和权益跨区域通用？ | 决定跨区交换、转换和套利边界 | 用制作—运输—拆解的最小例子核算 |
| Q04 | 初始资源怎样分配，新增地区怎样获得资源？ | 避免无法启动或无限开区增发 | 比较公共储备、迁入资源、再生与有界初始额度 |
| Q05 | 地块、蓝图、共同作品和公共设施由谁管理？ | 影响共建、署名、维护与新人进入，需满足 C16、C17 | 设计使用权和变更流程，做冲突及封锁案例演练 |
| Q06 | 第一版表现与交互形式是什么？ | 影响引擎和工期，不能由愿景直接推出 | 比较简单二维、低复杂度三维及必要的交互原型 |
| Q07 | 内核、存储、脚本和网络技术如何选择？ | 影响可测试性、隔离和运行成本 | 围绕首个实验做小规模技术验证 |
| Q08 | 第一轮具体增加什么机制，怎样验收？ | 决定研究—构建—测试能否对齐 | 使用[提案模板](templates/iteration-proposal.md)选一个有边界的目标 |
| Q09 | 运行预算由谁承担，子 Agent 如何分配额度？ | 影响是否能持续运行及参与规模 | 记录实际成本后制定上限与优先级 |
| Q10 | 哪类变化可以自动发布，哪些需要更高层决策？ | 影响自动化效率与世界连续性 | 先定义影响范围、硬约束、停止条件和恢复方式 |
| Q11 | RSI 在本项目中的确切含义是什么？ | 影响是否研究递归自我改进或价格指标 | 待明确缩写；当前不自动纳入必做范围 |
| Q12 | 是否需要区块链，具体解决什么信任问题？ | 影响权威状态与验证边界 | 先明确单运营方、多运营方和外部资产的需求 |
| Q13 | 哪些知识需要以模型训练解决？ | 避免把所有学习都误当成权重更新 | 先比较规则、程序技能、检索记忆和模型训练 |
| Q14 | 规则不再维护时怎样处理依赖它的世界？ | 影响长期作品连续性 | 明确版本支持期、兼容与迁移方案 |
| Q15 | 技术知识何时公开，如何传播，是否存在组织和许可边界？ | 决定共同进度怎样惠及后来者；许可制度需符合 C16、C17 | 比较开放知识、组织知识、独立实现与许可设计，分别核算知识传播和实体制造 |
| Q16 | 原始开局如何同时支持有限生存条件与无需强制劳动的参与？ | 防止早期玩法与 C03 冲突，也避免虚构无限启动福利 | 用有限启动储备、协作和有预算的服务做小规模体验实验 |
| Q17 | 后入者进入哪里，能使用什么基础服务与创作空间？ | 决定成熟文明是否真正改善新人体验，不能把永久封锁作为无约束选项 | 对照不同地区、访问权、价格、等待、替代路径及公共支出来源 |
| Q18 | 希望文明以何种节奏发展，自动化、离线运行与执行额度如何配置？ | Agent 可以持续活动，但计算费用、世界时间与产能不是同一变量 | 固定资源与模拟时间，比较活动和预算组合，依据实际瓶颈讨论参数 |
| Q19 | 是否允许地区衰退、灾难、赛季或独立重开，历史怎样保存？ | 决定持续性与维护成本；用户尚未指定这些制度 | 区分知识、设施、服务、正式世界与自愿分支，演练停供及恢复 |
| Q20 | 文明按全球、地区还是多层口径描述，怎样判定某项能力已经成熟？ | 避免少数先进设施代表所有居民，也避免工业指标覆盖文化选择 | 先测实际服务与可达性，再讨论可解释的阶段描述 |
| Q21 | 初版技术形成采用固定配方、组件组合还是实验发现？ | 决定玩法、模拟复杂度及研发边界 | 围绕一项可复用技术比较实现和体验；新增基础规律的权限继续由 Q02 约束 |
| Q22 | 哪些基本参与与创造能力必须保持可进入，其成本和等待边界是什么？ | 将不得封锁入口转成可验证的具体目标 | 选代表任务并登记质量、预算、时限和替代交付条件 |
| Q23 | 适度先发优势如何衡量和约束？ | 没有垄断也可能存在不断扩大的能力差距 | 比较同类任务中的功能、产能和进入成本，研究成长曲线、容量与长期回报 |
| Q24 | 哪些稀缺经营权可附期限、接入或服务条件，怎样保存私人作品？ | 兼顾投资回报、进入机会、退出自由与持续历史 | 在授予前定义义务，演练暂停、续期、替代和迁移；不默认突然没收 |
| Q25 | 如何观察共同控制、集团封锁与 Agent 分身，无法识别时怎样处理？ | 多账号和表面多供应者可能掩盖相同控制关系 | 以已知归属和行为证据做对抗测试，记录不确定性，不宣称完全识别 |

## 7. 后续更新约定

新的明确决定补充编号、日期、来源与影响文档。建议被采用时记录理由和验证结果；被放弃时保留失败原因。不要因为一个方案被多次重复，就自动把 P 或 Q 改成 C。

若后续任务明确授权某种实施或发布动作，以该次授权范围为准。此文件不代替实际运行授权，也不要求对所有可逆小改动逐项请示。
