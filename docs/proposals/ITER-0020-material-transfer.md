# ITER-0020 候选 · 居民自愿转让木材

2026-10-26。**仅契约草案，尚未采用、实现或验收。** 在 ITER-0019 动作竞争方案稳定后再决定实施。本文只定义一个可验证的合作增量，不采用资源再生、免费额度、预约队列或身份公平参数。

## 问题与采用边界

当前 r8 只有有限树木采集和材料建造，没有居民间转让。[连续世界契约](../contracts/continuous-world-v1.md)规定初始 12 木材、桥消耗 6、平台消耗 3。研究方在主目录的 `docs/research/2026-10-26-continuous/07-material-access-r8.md` 已记录真实 HTTP 反例：a1 采完 12，建桥后保留 6；a2 能过桥，但因库存 0 无法建平台。该证据运行的服务 DLL SHA-256 为 `1473453f8e35c7591b926926c7765bfbd239c1fcceaa356bebb9b65ada00d90f`；本文没有重新执行实验。

候选结果是：持有者愿意给付时，另一居民能接过既有木材并建成自己的作品；持有者拒绝合作时，仍如实保留材料入口失败。合作成功支持 C13—C15 的共建，**不能据此宣称 C16—C17 的先发优势与防垄断要求已解决**。a1/a2 当前同属 `local-operator`，两居民实验也不等于两个独立控制主体的公平实验。

建议最小语义为持有者主动赠送，收件人无需提交接受命令。赠送不产生债务、回报义务、费用或接收者的命令预算支出；本文没有双向交易、报价、自动索取、委托扣款或拒收流程。若产品需要接收者先同意，应另选“提议→接受”契约，不能把直接赠送同时宣传成双方同意。持有者“不愿给”属于控制方选择，不伪造成服务端转账拒绝事实。

## 候选命令与空间条件

动作建议如下；字段名称尚未冻结，不可向当前 r8 服务提交：

```json
{"type":"transfer","recipientActorId":"a2","resource":"wood","quantity":3}
```

发起人只从当前认证身份取得，不能在请求中指定来源账号。数量为正整数，单次不超过当前世界发行量 12；不能为 0、负数、小数或布尔值。收件人必须是同一实例中已存在且不同于发起人的居民；不按名字新建账号、不跨世界转账。转出的是本人现有库存，已建实体和未采树木均不可直接转让。

建议先做当面交付：双方当前距离不超过沿用的采集距离 1.6 m，且两位置之间按现有角色半径扫掠可通行。事务内同时读取双方位置、树、岩石和桥，防止隔障赠送变成远程物流。该距离和直线可通行限制是本候选的规则建议，尚未采用；不得通过移动收件人或放宽河岸碰撞来满足条件。路径规划只帮助赠送者接近对方，对方移动时须重新观察。

观察须显式宣告转让能力、资源类型与距离，客户端未识别能力时不显示为可执行动作。未来规则版本／能力版本及旧库启用方式待 ITER-0019 稳定后冻结；不靠升级服务悄悄开启旧世界的新经济动作，也不重建世界来隐藏已有材料被占有的历史。

人类入口须明确显示收件人和数量；Agent 任务须另有显式转让授权，冻结收件人、数量与木材支出上限。现有 `allowBuild`／`allowGather` 不包含赠送权限，模型不能改收件人或金额。转出材料计入任务累计支出，但单列为赠送，不冒充制造消耗；收到材料不自动扩大原建造预算。无材料或对方不愿合作时终止该有界尝试，不无期限等待或替用户扩大授权。

## 原子事实与恢复

沿用认证、持久 `World-Instance-Id`、规则检查、原命令 ID、语义哈希、事务账本与持久回执。原请求的收件人、资源、数量、版本锚点和前置模式都参与哈希；相同 ID 改任一语义字段产生冲突。双方共享一个算术事实：

`senderAfter = senderBefore - q; recipientAfter = recipientBefore + q`

同一个写事务完成以下步骤，任一步失败全部回滚：

1. 认证与实例校验；先查发起人原回执，同参数则返回原字节，不再次检查新余额或新距离。
2. 按冻结的前置模式检查旧意图，重新核实收件人、空间条件、当前转出余额和接收库存上限。无材料时返回持久拒绝；不赊账、不先记债务、不部分成交。
3. 守卫扣减发起人 q，增加接收者 q；新增一条世界事件、一条 `inventory:<sender>` → `inventory:<recipient>` 的资源账、一份发起人回执，然后提交。世界版本与事件游标各递增一次，`issuedWood` 不变。

建议成功回执结果包含 `action/resource/quantity/senderActorId/recipientActorId/inventoryWood`，最后一项是发起人在此次提交后的库存。公开事件包含双方 ID、数量、原发起人命令 ID 和提交版本；不要求公开收件人的完整余额。收件人通过本人的观察和可追溯事件确认入账，不能拿自己的 token 查询发起人的私有命令回执。原始归属键是 `(worldInstanceId, senderActorId, commandId)`，不能只用跨居民可能重复的 commandId 关联材料事实。

双方余额、事件、账本、回执必须在停服后核对一致；先读到库存增加本身不是“这笔赠送完成”的充分证据。赠送者已完成的回执不因收件人随后花掉木材而变为失败；报告分别记录已完成赠送和当前库存。收件人后续造平台仍是另一条独立命令，不能把转账回执写成已完成建造。

超时、断线、401、5xx、实例不符或损坏回执均保留原 pending。只在匹配原实例的查询明确返回 `COMMAND_NOT_FOUND` 时原样重发；不得换收件人、金额、锚点、模式或 ID。持久业务拒绝核对通过后才可结束该尝试；需要重试时重新观察并作新意图，继续累计原任务预算。查询和重放不再扣材料或计作第二笔赠送。

## 必须与并发条件一起处理

研究方的 `08-action-preconditions.md` 候选按观察后是否存在本人成功事件判断本人状态过期，当前 r8 尚无外部改动本人库存。赠送会打破这一前提：event 的发起人是 a1，受影响居民却有 a1 和 a2。

具体反例：a2 在版本 E 观察库存 3，冻结消耗 3 的平台建造；a1 随后向 a2 赠送 3。若只查 `event.actorId == a2`，a2 的旧意图仍可能被执行，回执库存为 3，而当前 Python 建造校验依据冻结库存预期为 0。这不是通过删除库存校验就能修复的问题。

因此转让启用的前提是：**所有按本人状态放宽全局版本的命令，都将成功转入视为接收者状态已变化**。可采用完整受影响居民集合或明确的接收者事件判据，具体实现与 ITER-0019 对齐；必须同样覆盖发送方、接收方的旧 walk/gather/build/transfer。历史事件仍按其真实影响读取，不能因缺少新字段假定所有旧事件都无影响。位置／余额变化后又回到原值也不能消除已经发生的状态变化。

转账请求若使用放宽模式，发起人原状态须未变化；接收者的当前位置和接收能力在事务内重验。接收者在此之前走动或合法支出不天然否决赠送，只要当前交付条件成立；赠送提交后才使接收者更早的意图过期。严格模式仍执行原全局版本规则，已保存的旧 pending 不自动升级模式。

## 可观察验收与否决条件

下表是未来验收要求，**通过数目前为 0**。测试用隔离 `.local` 数据和回环端口，保留首次失败证据，结束后停止自启服务；真实模型调用不是该机制验收的前提。

| 情形 | 必须看到的实际结果 |
|---|---|
| 合作后创造 | 合法采完 12 → a1 建桥花 6 → 双方当面交付 3 → a2 建平台花 3。最终自然 0、a1 库存 3、a2 库存 0、桥 6、平台 3，总量 12；双方命令与作品所有者可追溯。不能用管理员补料或直接改库准备材料。 |
| 持有者拒绝合作 | 等价初态中 a1 不发赠送命令；a2 可以走桥，但平台命令持久拒绝且不扣料、不造实体。报告明确“无自愿转让，独立建造入口仍失败”，不能把可走桥算为 C17 通过。 |
| 没有足够材料 | 发起人仍尝试赠送时得到可查询的持久拒绝，双方余额与世界版本不变；不能把该拒绝归因于对方主观拒绝。 |
| 身份、数量与交付范围 | 自赠、未知收件人、伪造来源、错误资源、非法数量、远距离、隔障、接收者走出范围均无材料变更；错误响应与持久业务拒绝分开断言。 |
| 同 ID 与同余额竞争 | 相同 ID 原样重放一次效果；改收件人／数量／模式冲突。同一余额同时赠送与建造不得双花；双方重用相同 commandId 不串回执。 |
| 外部入账使旧意图过期 | 先冻结 a2 的各类动作，再由 a1 给 a2 入账；原 a2 意图按冻结模式持久拒绝。确认后新观察、新意图可继续；无缺字段降级或清空累计预算。 |
| 提交前退出与扣款中途失败 | 原实例恢复后，要么完整原转账成立，要么双方都未变；原 ID 重试后恰好一条转账账本。不能只有扣款没有入账。 |
| 已提交丢回包与重启 | 原 ID 查询返回原字节；收件人已用材料建造后再查询，仍返回那次赠送事实，不再次入账。重启同库保持身份、账与作品；同 URL 换库不重放旧 pending。 |
| 客户端完成条件 | Python／人类入口实际交付并分别显示赠送、收到、建造事实。缺失／错配 sender、recipient、q、instance、执行版本或库存依据的回执不清 pending；移动端与旧报告仍可读。 |

若只验证服务端 200、余额总和或赠送方界面，不能接受“合作创造已完成”。若合作成功但拒绝合作仍无入口，则只采用自愿合作能力，继续保留材料入口问题；不能用赠送替代有界供给／独立生产路径的研究。
