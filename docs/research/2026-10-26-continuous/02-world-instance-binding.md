# 原命令恢复需要绑定持久世界实例

2026-10-26。研究建议，未改正式协议或服务源码。基线 `0639ef331a1bfd44de0712a45daf8ca59c6d5692`。本项独立于构建方正在修复的 Godot 多进程 pending 存储与切换服务画面问题。

## 已验证的反例

当前 `foundation-01` 是所有实例共用的路由名称，不是数据库实例的唯一身份。把一份新数据库放到原地址后，`URL + worldId + actorId + rulesVersion + stateVersion` 仍可全部相同。

隔离实跑步骤：

1. 在世界 A 观察初始 r7 状态，为 a1 保存 `gather tree-west-north`，`expectedStateVersion=0`，不提交。
2. 停止 A；在同一个 loopback 地址启动另一份新数据库 B，使用 **B 自己的新凭据** 认证。
3. 在 B 查询原命令 ID，收到 `404 COMMAND_NOT_FOUND`。
4. 向 B 原样提交 A 的命令，收到 `200 committed`；B 的 a1 获得 1 木材，版本变为 1。
5. 停止专用进程，只读检查两份 SQLite：A 的 a1/a2 木材均为 0；B 的 a1 为 1，a2 为 0。

两份观察的 sessionId 不同；固定 worldId、actorId、rulesVersion 和初始 stateVersion 相同。Godot 当前 `sha256(endpoint + "/foundation-01/" + actorId)` 存储绑定相同。

证据：[无凭据结果](evidence/world-binding-r7.json)、[可复跑探针](probes/world-binding.py)。原始本机目录 `.local/research/world-binding/20261026T021549Z-ce0a96/`。这是实际 HTTP 与停服数据库证据，加上 Godot 键推导；没有把它写成原生客户端端到端重现。0 次模型调用，全部专用进程已停止。

这是“同地址换新数据库并重新认证”条件下的跨世界误恢复，不是普通服务重启丢回执，也不是旧凭据能访问新数据库。当前正式契约已说明端口和目录隔离实例；本研究提出的是继续发展为持久世界时需要补齐的身份边界。

## 为什么现有字段不足

| 字段或机制 | 实际含义 | 不能独自承担的职责 |
|---|---|---|
| URL | 网络入口 | 同地址可以改指新数据库；同数据库也可以搬地址 |
| `worldId=foundation-01` | 固定路由名 | 区分两个独立新建世界 |
| `actorId=a1` | 世界内居民 ID | 在不同世界之间证明居民连续性 |
| sessionId/token | 可轮换或过期的认证会话 | 作为持久世界身份；会话轮换后同居民仍须查原回执 |
| rulesVersion | 规则契约 | 区分使用相同规则的世界 |
| stateVersion | 单世界修改序列 | 证明两个相同数字来自同一条历史 |
| commandId | 当前世界当前居民的幂等键 | 证明命令原本属于哪一个数据库实例 |

源码：`Protocol.WorldId` 固定；`WorldDatabase.Initialize` 给每个新库播种同一 worldId；`WorldService.Execute` 在当前库中查询原回执；Godot `_key()` 与 Python mission binding 都没有持久实例标识。浏览器 pending 保存 sessionId，但该字段也不能代替世界身份。

## 建议的最小实现边界

建议先解决新数据库替换这一条反例，不同时引入跨世界资产、身份联邦或分布式存储。

1. 新建数据库时生成随机 `worldInstanceId`，随世界状态持久保存。普通重启、会话轮换保留它。不能每次进程启动生成，也不能从 URL、token 或当前版本计算。
2. observation 与标准响应显式返回该值；恢复记录、mission binding 同时冻结它。客户端连接到不同实例时保留原记录，并说明它属于另一个世界，不自动套用到新世界。
3. 写命令携带原实例前置条件。服务在同一个写事务内校验后再处理回执和执行；只做客户端比较会留下观察后地址切换的窗口。字段名和 schemaVersion 由正式契约决定；当前严格解析器拒绝未知字段，不能直接给 r7 追加请求字段后假装兼容。
4. 实例不匹配是当前提交未执行的前置条件失败，不能因此证明 A 的原动作未发生，不能将 A 的 pending 结算或删除。也不应在 B 保存一份冒充 A 原命令结论的业务回执。
5. 新协议回执核验包括实例。查不到原回执只表示当前实例当前居民未找到；只有已确认实例一致，原样重试才有意义。

旧世界和旧 pending 的兼容需要单独写明。现有场景不自动迁移，不能在读观察时偷偷写库；旧 pending 缺少实例 ID，也不能用“当前连接成功”反推它属于当前库。可先在新场景要求完整绑定，保留旧场景原有行为与明确局限，再制定显式迁移。

本方案不声称解决备份回退、同一数据库克隆后双端同时写或历史分叉。复制数据库会复制实例 ID；如果后续支持这些操作，需要明确“恢复原历史”与“创建分叉”的规则及回执保留边界。当前不用为此提前搭建完整 epoch/租约系统。

## 可观察验收

| 情形 | 必须观察到的结果 |
|---|---|
| 同库普通重启，原提交已成功但响应丢失 | 实例不变；查询返回原回执；资源和事件只增加一次 |
| 同库轮换会话，同一个 actor | 实例不变；新会话能查询历史回执；回执历史 sessionId 不被重写 |
| 同 URL 新库，actor/rules/version 都相同 | 实例不同；原命令不能提交到新库；原 pending 保留 |
| 观察 A 后、POST 前服务改指 B | 服务前置条件拒绝；B 的世界版本、资源、实体与事件不变 |
| 重连 B 时本地仍有 A 的 pending | B 可被识别为新实例；A 记录不被覆盖、清除或改写 ID |
| 旧格式记录或旧协议世界 | 按明确兼容分支处理；不伪造实例 ID，不宣称获得新协议保护 |

上述是交付给构建方的验收建议；本轮只实际执行了前述 HTTP 反例，尚无修复后的通过证据。
