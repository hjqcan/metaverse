## 1. 建议选择

采用 **数据库持久实例 ID + HTTP 前置条件头**。只在新建 r8 库启用，仍为 r8/存储版本 8，不另开 r9。原命令 JSON、schemaVersion、rulesVersion 和语义哈希保持既有含义；旧 receipt 的 JSON 原文不重写。客户端在业务 payload 之外持久保存实例绑定，恢复时仍发送原 body。

这一选择比给每个历史命令追加实例字段更适合现有“原请求与原回执不可改写”的实现。它仍是明确的协议能力升级：有实例标识的世界要求前置条件，旧客户端不能继续无条件写入。不能同时声称“旧无绑定客户端照常写”与“所有写入都有实例保护”。

本轮解决独立新库复用同地址；不加入世界联邦、自动发现地址、资产迁移、热换数据库、备份回退裁决或克隆双写。

## 2. 实例的生成与旧库采用

建议新增独立元数据表，而不把连接地址或认证会话当作世界身份：

```sql
CREATE TABLE world_instance(
  singleton INTEGER PRIMARY KEY CHECK(singleton=1),
  instance_id TEXT NOT NULL UNIQUE,
  binding_version INTEGER NOT NULL CHECK(binding_version=1)
);
```

`instance_id` 用 `w_` 加随机 UUID 的 32 位小写十六进制表示。格式在应用层验证；恰有一行。初始化后禁止 UPDATE/DELETE，可用简单触发器保障。它不是凭据，不提供额外权限。

| 数据状态 | 行为 |
|---|---|
| 新建 r8 数据库 | 与播种同一事务生成并保存 ID；只有事务提交后的 ID 有效 |
| 新建历史 r1—r7 场景 | 保持历史协议，不为测试夹具和旧客户端引入新的必需头 |
| 已有该表且有效 | 只读使用原 ID；普通启动、重启和 issue-session 不改 ID |
| 旧数据库没有该表 | 保持 legacy 模式，不在启动或 GET 中自动改库，不宣称具有实例保护 |
| 有表但空行、多行、格式错误或版本未知 | 视为损坏/不支持，明确启动失败；不降级 legacy、不再生成 ID |

旧库采用是**后续可选工作，本轮不实现、不执行**。如果后来需要，可提供一次显式离线管理命令 `adopt-world-instance`，仅操作已存在且场景/版本有效的数据库；在停服状态的一个事务内创建表并插入 ID。重复执行返回原 ID；中断回滚后可重做。不能创建一个不存在的世界，也不能改 stateVersion、事件、资源、作品、会话、历史回执或 `PRAGMA user_version`。实例元数据版本与场景存储版本分开。

采用前后对业务表做逻辑内容指纹比对；旧库不是二进制文件完全不变，因为新增元数据本身会改变数据库文件。旧版本服务无法理解新约束，采用后不能把降级运行旧二进制当作受保护状态。

## 3. HTTP 边界

建议请求/响应头使用 `World-Instance-Id`，避免新定义 `X-` 前缀。后者依据 [RFC 6648](https://www.rfc-editor.org/rfc/rfc6648.html)；这里的具体字段为本项目应用协议，不是标准已登记的世界协议。

有标识的世界在 observation 中追加：

```json
{
  "world": {"id": "foundation-01", "instanceId": "w_0123456789abcdef0123456789abcdef"},
  "commandBinding": {"version": 1, "required": true, "header": "World-Instance-Id"}
}
```

其余 world 字段照常返回。所有成功的世界读取、命令响应和回执响应携带同值响应头；响应头是服务对本次所访问数据库的声明。历史回执的 status、JSON 字节和历史 sessionId 不因此变化。读取旧库 legacy observation 时保持原格式，不伪造 ID。

| 请求 | 有标识世界的规则 |
|---|---|
| 首次 observation | 允许不带头，以便发现实例；body 与响应头必须一致 |
| 后续 observation / events / proposal 读取 | 新客户端均带已绑定 ID；服务收到该头就必须校验 |
| POST commands、GET commands/{id} | 必须带且匹配实例；在执行/查回执的同一个事务快照内校验 |
| DELETE session | 作为修改请求同样要求实例匹配，再撤销当前认证会话 |
| 无头的旧客户端只读观察 | 可以读取；不能借此绕过修改与回执查询的前置条件 |

认证仍先于业务访问。写入流程为：开启现有 `BEGIN IMMEDIATE` → 事务内认证 → 读取并校验实例 → 查原 receipt/语义哈希 → 既有规则与版本校验 → 原事务提交。匹配实例后，原回执仍先于规则/状态版本检验返回。不要在业务修改之后才比较实例，也不要只在客户端比较。

实例标识只由服务器读库获得；客户端不能靠请求头设置或修改它。头名大小写不敏感，值精确比较；重复、逗号拼接、空值和格式错误返回 `400 INVALID_WORLD_INSTANCE`，不任取其中一个。若代理移除了头，按缺失处理，不退回无绑定写入。

| 条件失败 | 建议 HTTP / code | 结果语义 |
|---|---|---|
| 有标识世界要求头但缺失 | `428 WORLD_INSTANCE_REQUIRED` | 本次请求没有执行；需升级客户端 |
| 提供合法 ID 但与当前库不同 | `412 WORLD_INSTANCE_MISMATCH` | 当前库没有执行本次请求；原世界命令结果仍未知 |
| 已绑定客户端访问无标识 legacy 世界 | `428 WORLD_INSTANCE_UNAVAILABLE` | 服务不提供该绑定能力；不能静默移除头再提交 |

428 用于要求前置条件，412 用于请求头前置条件不成立；依据 [RFC 6585 §3](https://www.rfc-editor.org/rfc/rfc6585.html#section-3) 与 [RFC 9110 §15.5.13](https://www.rfc-editor.org/rfc/rfc9110.html#name-412-precondition-failed)。新错误沿用 `Cache-Control: no-store`，`mutated=false` 仅陈述本次当前库操作；不带 `status:rejected`，不新增业务 receipt、不改变世界版本/事件/资源。

客户端不能把 412/428 当成原动作的已确认业务拒绝，不能删除 pending 或换 ID 重做。网络故障和 503 仍保留 `mutated=null` 的既有语义。响应头缺失、不匹配或 body/header 不一致也不能结算原命令。

## 4. 客户端持久记录与换地址恢复

新 pending 外层建议 `recordVersion=2`，冻结 `instanceId/worldId/actorId/commandId/body`。`body` 是保存的原 JSON 字符串；实例 ID 作为传输前置条件单独保存。凭据不进入记录。

新版记录索引用 `instanceId + worldId + actorId`，每命令独立文件仍沿用 QA-001 方案。endpoint 作为来源与最近连接信息保存，不再作为世界身份的唯一组成。完成标记仍绑定原 commandId 与 body 哈希；同时受实例目录约束。

| 重连情况 | 处理 |
|---|---|
| 同实例、同居民、换会话 | 允许查询和恢复；不要求回执历史 sessionId 等于新会话 |
| 同实例、同居民、换 endpoint | 允许恢复：先在用户指定的新地址用该地址凭据观察，验证同实例和居民，再加载同一 pending；原 body/ID/规则/预算不变 |
| 同 endpoint、不同实例 | 不加载或重试原实例记录；保留并显示它仍待在原世界确认。明确连接新世界后，新世界可有自己的独立 pending |
| 同实例、不同居民 | 不查询、结算或挪用另一居民记录 |
| 同实例但规则改变 | 原 pending 仍可查原回执；原请求不改 rulesVersion。后续任务如何采用新规则另行处理 |

不把旧 token 自动转发到新地址，不自动跟随重定向寻找世界。实例 ID 不是服务器真实性的密码学证明；本方案沿用现有受信本地/配置端点边界，不承诺对恶意冒充服务器有效。

Python mission 应把身份绑定与 endpoint 分开：冻结 `instanceId/worldId/actorId/rulesVersion/spec/origin`，来源地址保留为历史信息。用户明确用新 URL 恢复同一 state 文件时，先核对实例与居民；不能因为换地址重置累计预算、重新选择目标或把已完成任务再次执行。这里无需新增自动迁移 API。

## 5. 旧客户端与旧 pending 的边界

旧客户端连接未采用实例元数据的 legacy 世界，仍按既有契约工作；这条路径保留历史兼容，也保留 [02](02-world-instance-binding.md) 已证实的局限。新版客户端可沿用独立 legacy 分支支持这些世界，明确显示其无实例绑定保护；不能把已受保护的任务/记录降级后写入 legacy 世界，也不能宣称已有预览库自动获得保护。不要为了通过新验收重建或清空原库。

旧客户端连接已标识世界，观察仍可用，无头写入及回执查询返回 428。它可能留下待决记录，不能由服务为了兼容而悄悄放行。

**旧 pending 没有实例 ID，就没有足够证据自动关联当前库。** 新客户端保留原记录为 `legacy_unbound`，不把“URL/actor 相同”“当前认证成功”“命令查询 404”当作补写实例 ID 的依据。相同 endpoint/actor 下存在该类未决时，应明确阻止替代性新动作，直到原记录有可核查的处理结果；不能用清空存储解决。

区分两个格式分支：合法旧格式在 legacy 世界继续原有恢复纪律，并保留该模式的局限；转到已标识世界时成为待核对来源的旧记录。声明 `recordVersion=2` 的新保护格式则必须有合法实例 ID，缺失/空值属于损坏，不能把它悄悄解释成旧格式或从当前观察补值。保留原文件并报告存储/绑定错误，不跳过它后对同一绑定发送替代新动作。首版无需构建通用迁移/隔离管理后台。

未来升级旧世界的路径是在仍能确认原世界的旧服务/客户端下先结清旧待决，再离线采用实例标识、更新客户端；若旧结果尚无法确认，保留原记录和世界，单独处理其来源证据。本轮不增加一个“点击即可把任何旧 pending 绑定当前库”的工具，也不伪装已完成旧记录自动迁移。
