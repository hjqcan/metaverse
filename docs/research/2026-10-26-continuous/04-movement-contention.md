# r8 多居民进展：全局版本竞争的可构造反例

2026-10-26。后续研究项，不建议插入正在实施的实例身份修复。基线 `b89d44a301621da4c32183f78b8f0879ff862ad9`；使用独立复制的服务二进制和新测试库。

## 实跑事实

按明确排程重复 20 次：a2 观察 → a1 观察同一版本 → a1 向自己的当前位置发 `walk` → a2 提交原版本的合法 `walk`。

| 结果 | 实测 |
|---|---:|
| a1 零位移 walk 提交 | 20 次成功 |
| a1 实际位置 | 始终 `[5,7]` |
| a2 明确 `STALE_STATE` 拒绝 | 20 次 |
| a2 实际位置 | 始终 `[26,17]` |
| 干扰阶段世界版本 | 从 0 增至 20 |
| 停止 a1 后的对照 | a2 向同一目标提交一次成功，实际移动 0.1 米 |

停服 SQLite 核查：最终版本 21、事件 22、committed receipt 21、rejected receipt 20；自然木材仍为 12，个人库存 0，完整性通过、外键错误 0。全部专用进程已停止，模型调用 0。

证据：[结果](evidence/movement-contention-r8.json)、[探针](probes/movement-contention.py)。本机原始目录 `.local/research/movement-contention/20261026T022404Z-c4dd41/`。

这是人为控制交错顺序的 HTTP 进展反例，不是自然发生概率、延迟压测或真人 Godot 体验。没有运行真实 resident mission，不能把 20 次拒绝称为“实际任务耗尽”。Godot 当前只在方向非零时发 walk，也不能由此声称闲置原生客户端自动产生这些请求。

## 解释与边界

服务的状态与回执是自洽的，原命令幂等没有失效。问题在于所有居民动作共享一个 expectedStateVersion；即使另一个居民未发生空间位移，walk 仍更新移动时钟/额度并提交一条版本与事件。一个有限预算的居民可以一直被更早提交者打断。

现有 `continuous_api` 已有单次旧版本拒绝测试，证明并发不会用旧快照写入；本探针补的是持续进展边界。二者分别回答一致性与是否能完成动作，不能相互替代。实例 ID 解决跨世界恢复，也不会消除同世界版本竞争。

## 建议下一步

先用两个真实客户端同时走不同岸边路线，记录每个居民的已确认移动距离、成功数、STALE_STATE 数、完成时间和累计命令预算；改变提交相位，保留独立冷启动对照。先确认实际阻塞程度，再选改动。

可比较：客户端避免已知零位移并在明确拒绝后退避；服务避免无实际位移造成无效全局版本推进；进一步为移动设置居民或相关环境的前置条件。前两者只能缓解，不能保证对抗性排程下无饥饿。后一项会影响 `expectedStateVersion+1` 回执校验与现有测试，不能直接忽略版本检验或把有歧义的请求换 ID 重做。

本轮不提出大规模实时服务器重写，不把当前实验的 100% 拒绝率外推为正常双人体验。采用门槛应来自真实双客户端结果与任务预算，而不是只统计总 TPS。
