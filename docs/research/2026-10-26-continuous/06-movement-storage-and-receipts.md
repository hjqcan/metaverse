# 连续移动的持久化容量与原回执保留

2026-10-26。后续容量研究，不改变当前实例绑定实现或删除任何世界记录。

## 测量结果

在独立 r8 服务中执行 2,000 条成功 walk，目标在无障碍短区间内交替。服务仍按自己的速度额度裁决实际位移；请求加速生成，只用于得到足够的存储样本。使用之前冻结的 `b89d44a` 阶段服务二进制，SHA-256 为 `5d0ca45b644374321fe523886bb516ba3bf15a932688e10540e7d6858cf8d5d7`。

| 停服数据库指标 | 之前 | 之后 | 差值 |
|---|---:|---:|---:|
| 文件/已分配页字节 | 122,880 | 1,728,512 | 1,605,632 |
| receipt 行 | 0 | 2,000 | 2,000 |
| event 行 | 1 | 2,001 | 2,000 |
| receipt JSON 字节 | 0 | 687,641 | 687,641 |
| event JSON 字节 | 132 | 323,773 | 323,641 |

本样本每条动作平均增加约 **803 字节数据库分配**，其中回执与事件 JSON 合计约 506 字节。数据库完整性检查通过；没有采集或建造，仍为 12 自然木材。专用进程已关闭，模型调用 0。

证据：[完整结果](evidence/movement-storage-r8.json)、[探针](probes/movement-storage.py)。本机目录 `.local/research/movement-storage/20261026T023521Z-94c8c7/`。没有把本机加速生成所需的 4.27 秒当作多人吞吐能力或正常网络延迟。

## 容量情景，不是长跑结果

用本样本的平均已分配字节线性外推，每名居民持续活动 24 小时：

| 平均已提交动作频率 | 每日 receipt 数；另有同量 event | 估算新增数据库分配/日 | 估算 30 日 |
|---|---:|---:|---:|
| 1 次/秒 | 86,400 | 66.15 MiB | 1.94 GiB |
| 5 次/秒 | 432,000 | 330.75 MiB | 9.69 GiB |
| 12.5 次/秒 | 1,080,000 | 826.88 MiB | 24.22 GiB |

当前 Godot 已提交 `e25814d` 的移动 cooldown 为 0.08 秒，12.5 次/秒只是忽略往返时间和 busy 限制的理论上界；Python 连续执行器按 0.6/3 秒的额度等待。实际频率、在线占比和并发量需实测。两名持续活跃居民的行数约翻倍；普通人每天仅短时游玩的情况应按实际活跃秒数计算。

上述不是 30 日数据库实测。样本小，页利用率、索引、长版本号、小数坐标、拒绝回执、备份和 WAL 峰值均会改变实际占用。它只说明逐步移动留下永久回执/事件不是零成本，应在常驻居民规模增加前测量。

## 原命令恢复约束不能在清理时丢失

当前契约让原命令 ID 查询返回原业务事实；成功、拒绝与未知结果有不同语义。直接按时间删除 receipt 后，旧 pending 可能先得到 404，再因旧 stateVersion 获得新的 STALE_STATE 拒绝。虽然版本检验可阻止原请求再次执行，但“原动作曾成功”这一事实会被替换为新拒绝，任务可能据此另发替代动作。

这是根据现有查询/重试流程得到的风险推演，本轮没有在用户数据库删除回执，也未把它当作已执行的删除反例。按已声明的原回执契约，容量优化不能把“旧事实查不到”冒充“原动作确定未发生”。

建议先观测实际活跃频率、每小时记录增长和磁盘余量，再选择措施。可比较更低的网络动作采样配合客户端表现插值、避免已知零位移请求、保持原查询语义的归档/压缩。若以后把实时移动和经济动作采用不同持久化粒度，需要明确移动序号、恢复与任务到达证据的契约；不能直接丢掉现有 walk 回执后声称兼容。

这一研究不要求当前就拆分数据库、引入事件平台或上线自动清理任务。先把输入体验、多人进展、累计预算和存储增长放到同一测量里，避免只用画面帧率或单次测试通过判断常驻运行能力。
