# 多居民动作竞争：保留本居民次序，按当前世界重验动作

2026-10-26。回应构建方“04 的最小可实施契约”请求。**构建方已接受为 ITER-0019 待构建契约基线；尚未实现或通过候选验收。** 当前候选执行数为 0。只新增研究文件；没有修改服务器、Godot、Python mission 或旧数据库。经济候选也未因此采用。

## 推荐结论

为受实例保护的 r8 增加一个**逐请求明确选择**的 `actor-state-v1` 前置条件模式。保留 `expectedStateVersion` 作为原观察锚点；若锚点以后本居民已有成功动作，拒绝旧意图。若只有其他居民变化，则允许进入原有事务内的材料、距离、几何、速度和占地校验。世界全局版本仍按每次成功提交递增。

缺少模式字段的全部旧请求继续使用全局版本严格相等；不隐式改写旧 pending，不改变旧请求哈希或旧回执字节。新模式只解除“无关居民使整个观察版本过期”的拒绝，并不保证最后一份资源人人可得，也不取消本居民的次序约束。

最小实现可先查询现有不可变事件，**不必先加 actor 独立计数器、对象版本、空间分片、全局队列或新的物理规则版本**。新模式是否正式采用，仍由构建方的独立迭代确定。

## 哪些前置条件真正必要

| 范围 | 保留或调整 | 原因 |
|---|---|---|
| 身份、实例、规则与动作参数 | 保留认证、`World-Instance-Id`、r8、严格类型及配方校验 | 同 URL 换库、会话更换、错误动作不能借并发优化越过边界 |
| 同居民状态 | 原观察以后不能已有本居民成功提交 | 防止双客户端或乱序旧目标接在新动作后执行；位置相同不代表状态未变 |
| 跨居民远处 walk | 不要求全局版本仍等于观察值 | 当前角色之间不做实体碰撞；他人的走路不改变我的位置、库存、速度额度或目标材料 |
| walk 路径 | 当前速度额度、地图界限与完整 sweep 必须在提交事务内重算 | 桥和树的当前几何可能与原观察不同；不能信任客户端旧路径 |
| gather | 当前节点存在、有剩余材料、仍在本居民 1.6 m 范围内；原节点 ID 与数量不变 | 不要求节点剩余量恰好等于旧观察，只取当前允许的一份；最后一份仍只交付一次 |
| build | 当前库存足够、固定配方与目标不变、距离、完整占地、树岩和既有实体重叠检查 | 其他居民可能抢先占地；原观察的可建位置不是土地预约 |
| 回执与未知结果 | 原 ID、原请求、原实例和原模式不变；先查原回执 | 丢回复不能变成另一个动作，也不能给同一 ID 换锚点 |

这依赖当前 r8 的事实：所有居民状态改变都伴随该居民的成功事件；没有转让、伤害、推挤、管理员移动或其他 actor 直接改变本人库存。未来增加这类能力时，必须按受影响居民更新版本或记录完整影响集合，不能直接沿用“只看 event.actorId”的判据。

## 最小请求和事务契约

建议只增加一个可选请求字段：

```json
{
  "schemaVersion": 1,
  "rulesVersion": "r8",
  "commandId": "original-command-id",
  "expectedStateVersion": 74,
  "preconditionMode": "actor-state-v1",
  "action": {"type": "gather", "nodeId": "tree-east-north"}
}
```

`preconditionMode` 缺失时仍是现有严格模式；出现时只接受已知精确值，拒绝 null、未知值和重复字段。observe 增加明确的支持能力，例如 `commandConcurrency:{supportedModes:["actor-state-v1"]}`，仅在实例受保护的 r8 宣告；没有能力信息的客户端继续原模式。不要把传输实例保护头当成模式选择。

原哈希分支必须保持当前规范化字段及顺序。新模式把该字段纳入语义哈希；不能只放一个未参与哈希的 HTTP 头。同 ID 切换模式、动作或锚点必须冲突。旧服务不理解新字段时不得由客户端悄悄删掉字段重发同一 ID。

事务顺序建议：

1. 原有 `BEGIN IMMEDIATE` → 认证 → 实例条件 → 按 actor/commandId 查询回执。若已存在且哈希相同，原字节返回；不同则 `IDEMPOTENCY_CONFLICT`。
2. 读取当前世界版本 S 与本居民状态。旧模式执行现有 `E == S`，E 为原请求 `expectedStateVersion`。
3. 新模式只用于受保护 r8 的 walk/gather/build。要求 `0 <= E <= S`；未来锚点明确拒绝，不能用 `<=` 写反而接受。然后检查 E 以后有没有本居民成功事件：

   ```sql
   SELECT EXISTS (
     SELECT 1 FROM events
     WHERE world_id = $world AND state_version > $observed
       AND json_extract(event_json, '$.actorId') = $actor
   );
   ```

   为真则建议返回持久 `409 STALE_ACTOR_STATE`；为假只是允许继续校验。现有 `(world_id,state_version)` 唯一索引可限定扫描到观察后的区间，不必每次扫描全部历史求 max。非常旧的请求仍可能扫描较长区间，需以实际负载测量，不宣称规模问题已经解决。
4. 在**同一个写事务**调用当前 ValidateContinuous/WalkContinuous，重新读所需材料、实体和几何，再作守卫扣减、插入作品、世界版本 S+1、事件、材料账和回执，一起提交。对业务拒绝保存原 ID 的拒绝回执；实例/认证错误继续现有传输边界，不据此清除 pending。

SQLite 在同库中串行裁决写事务，`BEGIN IMMEDIATE` 先取得写事务资格；现有代码已经使用这条路径。因而材料/几何从校验到写入不应放到事务外，也不需要为这个改动另设应用级全局锁。单写入者仍可能等待或超时，并不提供请求公平性保证。[SQLite 隔离说明](https://www.sqlite.org/isolation.html)、[Microsoft.Data.Sqlite 事务说明](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions)

同居民两个请求来自同一观察时，先成功到达者消费该状态，另一个拒绝。这保证旧状态不能连续驱动多个动作，**不保证按客户端生成时间排序**。当前每客户端“有未知 pending 时不发新动作”的约束仍须保留；拒绝动作本身不改变居民状态，也不消耗新的 actor 状态。

## 回执和客户端必须一同改

当前 Godot `_settle`、Python `valid_walk_receipt` 和 `valid_gather_receipt` 都要求 `receipt.stateVersion == intent.expectedStateVersion + 1`。此外 gather 要求 `remainingWood == 旧观察剩余 - 1`。这些恰好依赖原来的全局 CAS，不能在新模式中照搬，更不能对所有旧请求直接放宽成“大于”。

建议**只给新模式回执**增加执行依据，仍作为同一不可变回执保存：

```json
"execution": {
  "preconditionMode": "actor-state-v1",
  "observedStateVersion": 74,
  "appliedOnStateVersion": 75
}
```

成功回执须满足：模式与冻结请求一致；observed 等于原 E；appliedOn 为实际事务读到的 S 且 S>=E；`stateVersion == S+1`。身份、实例、commandId、动作和明确终态仍须逐项吻合。业务拒绝的 `stateVersion` 为当时 S，不能冒充已提交。原回执重放不能把 appliedOn 改成查询时的新版本。

walk 继续按冻结的本居民起点验证最大单步与到目标的线段关系；同居民事件判据保证该起点未被更新。build 继续核对原目标、配方成本与实际实体事实。gather 继续要求原 nodeId、quantity=1、原本人库存+1；允许其他居民消耗目标节点，但建议新模式 gather 结果增加 `remainingWoodBefore`，要求它是事务内扣减前数量，`remainingWood == remainingWoodBefore-1 >= 0`，并在当前无再生的 r8 中验证 `remainingWoodBefore <= 原观察剩余`。这样保留明确的物料变化依据，而不是把所有数值检查都取消。

Godot 新模式 pending 应用新记录版本（例如 3），明确要求 body 含模式；既有 v2 继续旧语义。缺少字段、损坏记录不能降级；settle 仍只移除匹配原记录。Python 已有任务先按其冻结的协议模式完成；新任务选择能力后固定模式，原起点、预算、before 事实和 pending 不因重入重置。未适配的旧客户端始终走严格模式，因此仍安全但仍可能遭遇原有竞争。

同一条未知请求不能因重试而更新 E，不能换 ID，不能换模式。得到真实持久拒绝后，才可重新观察并把当前仍有效的意图作为新的命令；累计任务预算照常扣算。已经成功的旧请求，即使本居民又做过许多动作，也应先命中回执并原样返回。

## 备选比较与兼容范围

| 方案 | 能力与问题 | 本轮建议 |
|---|---|---|
| 增加重试次数或退避 | 可减少偶发碰撞；持续干扰时仍无进展保证，消耗原预算 | 不作为根本修复 |
| 只删除全局版本比较 | 同居民旧方向会在新动作之后继续执行，丢失原观察约束 | 否决 |
| 只比较当前坐标/库存 | 同居民走开返回等 ABA 会被当成未变化 | 否决 |
| 本居民独立 version 字段 | 查询成本固定，能扩展为受影响居民版本 | 合理后续选项；当前需加列/迁移/全写路径维护，不是最少改动 |
| 现有事件区间判定 + 当前动作重验 | 不变更旧状态存储；保留同居民次序并消除无关更新拒绝 | 当前优先候选 |
| 每资源点/空间区域都加版本 | 能表达更细读集，但须定义地形、重叠范围和生命周期 | 当前三种动作可直接事务内重验，暂不需要 |

物理规则 r8、世界实例、全局状态版本和事件游标都保持。缺字段的 r1—r8 请求与历史 pending 仍按严格模式处理；新模式只在保护 r8 明确宣告并接收。既有保护 r8 可以由升级服务提供能力，因为旧命令语义没有改变；不需要删库、重新发行材料或搬移作品。现有未保护 r8 继续旧路径，不由这个迭代顺带补身份。

这一候选依赖完整、不可变的提交事件；不能同时引入事件裁剪、匿名修改居民状态或“找不到历史便假定未变化”。未来若要裁剪，先换成可持续保存的居民版本事实，再独立验证兼容关系。[06 的存储研究](06-movement-storage-and-receipts.md)仍是尚待解决的独立约束。

## 独立迭代必须通过和必须否决的情况

| 验收 | 新模式必须达到的实际结果 |
|---|---|
| 04 同类 20 次受控远处 walk 干扰 | 另一居民不因这些无关提交得到 STALE；其真实位移发生，累计预算没有重置 |
| 远处 walk 插在观察和 gather/build 之间 | 原命令在材料和占地仍有效时真实成功；回执通过真实 Godot 与 Python 校验并清除原 pending |
| 同居民双客户端、乱序与 ABA | 同观察最多一个成功提交；旧请求不能因回到原坐标而恢复有效 |
| 两居民竞争最后 1 木 | 合计只增加 1 库存；另一方得到资源耗尽；账、事件和回执一致 |
| 两居民竞争同一建造占地 | 只形成一个合法实体；另一方占地拒绝且材料未扣；不得按旧观察直接写入 |
| 路径几何变化 | 仍按当前树/桥/河岸做 sweep，不能穿障或越过速度预算 |
| 已提交丢回复、未提交退出、服务重启 | 原实例+ID+body+模式恢复，只发生一次真实效果；原回执字节不变 |
| 错实例、错误/重复模式、未来锚点、模式改写 | 不产生世界动作；不能被自动降级成另一种请求 |
| 旧库与旧 pending | 缺字段仍严格检查，原哈希/回执/作品保留；不能宣称旧客户端竞争也已修复 |
| 伪造或缺损执行依据 | 客户端不清除 pending；测试必须覆盖 appliedOn 错误、模式不符、错误 node/quantity 与重复回放 |

只验证服务器 200 不算完成；只让客户端接受任意更高版本也应否决。新模式解决的是无关变化造成的虚假冲突，不能据此宣称资源公平、SQLite 调度公平或大量居民下的固定完成时限已经实现。
