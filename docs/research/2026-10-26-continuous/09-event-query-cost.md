# 事件锚点查询成本：新鲜观察便宜，旧锚点可能扫描长区间

2026-10-26。补充已冻结的 [08 并发候选](08-action-preconditions.md)。这是隔离 SQL 微测量，**不是 World.Server 并发验收**。候选规则执行 0、真实世界命令 0、模型调用 0；未修改任何现有世界或产品索引。

## 对构建的直接结论

保留 ITER-0019 的小范围契约，不必因本研究立刻增加 actor 计数器或索引。但验收应区分新鲜观察和“很久以前未提交、且本人一直没再行动”的原请求：原有世界版本索引只跳过观察以前的事件，不能跳过观察以后其他居民的全部事件。

本机 20 万条合成事件中，若观察后没有本居民动作，查询扫描完整后缀的中位时间约 69.10 ms、1200018 个 SQLite VM 步；只落后 20 条时约 0.0095 ms、138 步。若本居民动作很早就出现，EXISTS 可以马上结束，同样有 20 万条后续事件时仅 25 步。不能把“旧锚点”一概等同于慢查询，也不能把短区间结果外推到所有恢复请求。

已经提交且回执存在的恢复请求，按 08 的顺序先命中原回执，**不会走这个事件判据**。这里关注的是回执未找到、随后仍要裁决原请求的路径。

## 方法与证据

[脚本](probes/event-query-cost.py)在 `.local/research/event-query-cost/20261026T025622Z-5dfc51/` 创建两个独立 SQL 数据文件。它们不是可启动的世界库，仅包含查询所需的 events 表与世界标识。两份各有 200000 条合成 walked 事件，全部来自 a1；查询 a2 表示观察后没有自己的动作，查询 a1 表示首条即可命中。

events 使用当前的 `(world_id,state_version)` 唯一索引。一份保持该结构，另一份只增加候选表达式索引。两份事件内容 SHA-256 完全相同、完整性均 ok。

Python SQLite 3.45.1 只负责建立隔离数据。**计时查询使用从服务构建复制的 Linux x64 `libe_sqlite3.so`，实际返回版本 3.53.4**；通过原生 C API 以只读方式打开数据，未执行 .NET HTTP 服务。原生库 SHA-256 为 `eddcd4aa561d5b8f252db77e8272e7d1aed96bcab9fda3f177ca542f916290bf`。

每项先预热一次，再测已准备的 SELECT 七次，记录中位数、最小/最大值、VM 步数与查询计划。完整数据见 [结果 JSON](evidence/event-query-cost.json)。没有测冷缓存、HTTP 往返、写事务锁等待、并发吞吐或新增索引的持续写入开销。

| 观察后的事件 | 查询情形 | 原索引中位 ms / VM 步 | 加 actor 表达式索引中位 ms / VM 步 |
|---|---|---|---|
| 0 | a2 无后续动作 | 0.002887 / 18 | 0.002719 / 17 |
| 20 | 全是 a1，a2 无后续动作 | 0.009493 / 138 | 0.002690 / 17 |
| 2000 | 全是 a1，a2 无后续动作 | 0.634795 / 12018 | 0.002688 / 17 |
| 200000 | 全是 a1，a2 无后续动作 | 69.100945 / 1200018 | 0.002676 / 17 |

这些毫秒数只描述本机此次测量。更稳定的证据是同一查询语义下 VM 步数随未命中区间增长，以及查询计划实际使用的条件；两者也只对应记录的 SQLite 版本与数据形态。

## 候选索引的收益与代价

原查询计划使用 `world_id=? AND state_version>?`，再逐条检查 JSON 中的 actor。候选索引把 actor 放在版本范围之前：

```sql
CREATE INDEX research_events_actor_version
ON events(world_id, json_extract(event_json,'$.actorId'), state_version);
```

在隔离对照中，查询计划变成同时利用 world、actor 表达式与版本范围的覆盖索引，a2 不存在的情况直接返回。数据库文件从 38113280 增到 43909120 字节，增加 5795840 字节，约 5.53 MiB；这是该合成数据的索引空间，不是世界总存储估计。

SQLite 表达式索引要求查询中的表达式与索引表达式匹配；本研究已实际核对计划，而不是仅因 CREATE INDEX 成功就推断被使用。EXPLAIN QUERY PLAN 文本会随 SQLite 版本变化，不宜把本次字符串当作跨版本业务验收格式。[表达式索引官方说明](https://www.sqlite.org/expridx.html)、[查询计划官方说明](https://www.sqlite.org/eqp.html)

本轮不建议自动把该索引加到所有旧库。若后续实际恢复负载显示需要，再单独确认添加范围、建索引耗时、写放大与磁盘余量，并验证旧回执和世界状态不变。最重要的兼容边界仍然是：**不能为节省查询时间而丢掉老 pending、改写原观察锚点、换 commandId，或把“没扫完”当成“本人没变化”。**

## 与后续转让的关系

这个索引只加速当前 r8 的“提交者就是状态受影响者”判据。材料转入会改变接收者库存，即使 event.actorId 是提供者；索引再快也不能补上错误的影响范围。ITER-0020 草案由其他单独写入者负责，08 已要求它明确接收者状态失效。

届时应先选对事实来源，再谈查询优化：记录受影响居民集合、扩展转让事件的明确参与方判定，或维护实际受影响居民的版本，都可能成为候选；不能仅新增一个 sender 索引就宣称接收者旧观察得到保护。本研究没有采用其中任何一项，也没有更改 08 的冻结契约。

## 给 ITER-0019 的最小补充验收

除 08 的正确性矩阵外，保留三条时间与工作量观测：新鲜观察、回执未找到的旧观察且本人没变化、旧观察后本人已变化。原请求内容、终态和世界效果都必须正确，记录查询区间大小及耗时即可。

当前没有用户或构建方已批准的响应时限，不把 69 ms 当作通过或不通过的门槛。若未来确定端到端时限，必须再用实际 .NET 服务和并发写入测量，不能拿这里的原生 SELECT 时间代替它。
