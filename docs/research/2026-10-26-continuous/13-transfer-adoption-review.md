## 1. 版本允许范围与原请求匹配必须分开

新 r9 可以公布转让能力；旧 r8 的能力、材料规则、原请求与原回执不因此改变。`schema 9` 是数据库版本，HTTP envelope 与 command 的 `schemaVersion` 仍为 1，不能混用。

入口可支持两组明确映射：`r8 ↔ wilderness-continuous-v1`、`r9 ↔ wilderness-cooperation-v1`。但是，**结算回执必须匹配原请求的规则版本**，不能只验证“它属于 r8 或 r9”。建造实体的规则、报告中的规则也要匹配那条原命令。否则把所有 `== r8` 改成版本名单，可能把错误版本的伪回执认成成功。

从 `7907afb` 的已完成基线读取到的相关触点如下；构建中的新增分支由产品拥有者处理，不把这些尚待适配的位置报作最终缺陷。

## 3. 接收者失效与预算：直接入账不等于旧任务无成本继续

成功 `woodTransferred` 事件需要表达 sender 与 recipient。已有 `actorId=sender` 判据继续保留，新增影响条件可明确限定为“事件类型为 woodTransferred 且 recipientActorId 为本人”。它必须用于所有受支持的 actor-state 动作，包括旧 walk/gather/build 和新 transfer；失败转让不改变任何居民状态，也不产生成功转让事件。

本轮已选停止策略：入账发生后，接收者更早保存的动作若尚未执行，应得到可核验的 `STALE_ACTOR_STATE`，结清该原 ID 后停止旧路线／任务，等待显式新输入。已有任务累计命令不退回，收到材料不增加其原授权或预算。两边同时从同一个观察准备互赠时，先提交的转让使另一位旧请求失效，不应把两份旧请求都直接执行。

[原草案](../../proposals/ITER-0020-material-transfer.md)中的“赠送不产生接收者命令预算支出”需要限定为：**收款本身不提交一条接收者命令、不直接扣其额度；它可能使已计入预算的旧动作被拒绝，并停止当前任务。** 不能把一次入账记作接收者原平台任务已经完成。[10](10-transfer-and-recipient-progress.md)保留了相关候选反例，本轮最终策略是停止，不是三次自动重试。

另一方面，recipient 先移动或花掉自己材料，不必自动否决 sender 的旧转让：若 sender 本人状态未变，事务当下仍满足距离、扫掠、库存和身份条件，就可执行。不要把接收者旧位置冻结为必须保持不动的义务。

## 4. 最小授权、事实与原子账

人类发送时需明确收件人和数量；Agent 的转让意图需独立授权并冻结同样字段。`allowBuild`、`allowGather` 不隐含赠送许可；转让许可本身也不自动批准缺料后采集或建桥。接近移动与可能的后续尝试继续计入原有界任务，不无限追逐移动中的收件人。

材料支出分开记录“建造花费”和“实际送出”，但二者都受原授权上限约束。只有确认原转让成功才把 q 计入已送出；未知结果保留原请求与 before，原 ID 回查或重放不再记第二笔。没有接受命令不等于双方已表达同意，也不能从收件人库存增加推断其目标或委托发生改变。

发送者的最小成功证据应对应原实例、原 sender、原 recipient、resource、正整数 q、规则、命令 ID、execution 和 `senderAfter = frozenSenderBefore - q`。不需要为此公开接收者完整余额；接收者的实际旧余额由服务在同一事务读取和更新，原子核对属于服务与账本验收。

公开转让事件以 `(instanceId, senderActorId, commandId)` 关联，包含 recipient、resource、q 和提交版本。接收者可通过既有事件接口与本人观察识别入账；不能用自己的 token 查询 sender 私有回执，也不能只因当前库存恰好增加 q 就认领那笔事实。若界面尚未读取相应事件，应只显示当前库存，不虚构赠送来源。

扣 sender、加 recipient、唯一转让账、成功事件、世界版本与 sender 回执必须同一事务。sender 后来余额变化或 recipient 花掉材料，不使已完成转让失效。先查原回执，再检查当前余额、距离及 actor 状态。
