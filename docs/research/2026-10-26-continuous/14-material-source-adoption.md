# 材料来源采用前评审：有界输入、已知控制组与实际采集

## 建议采用的最小范围

采用一个独立候选场景：保留原四棵树和自愿赠送，新增一处不阻挡行走的生态采集区；补给进入自然材料账，居民按已知控制组预约后亲自采集。先验证“公共桥已存在、旧自然材料耗尽、持有者拒绝赠送”的后来者平台目标。此范围不包含无桥两岸同时获得入口、无限后来者、通胀率、私人土地制度或真实身份识别。

建议参数如下。数值用于小规模可复跑实验；构建方须在采用契约中确认或修改，不能把它们记成用户已确认的经济制度。

| 项目 | 建议值与语义 |
|---|---|
| 规则与实例 | 新 r10 候选，明确的新 scenario/storage；默认 r8 和已有 r1—r9 不自动改变 |
| 旧材料 | 初始12，原树不再生，旧桥、平台、库存、回执保留 |
| 来源位置 | 东岸中心 `[28,10]`，从创建时保留建造区域 `[27,9,29,11]`；始终不加入行走障碍 |

| 生产 | 开启后每10服务秒一次，实际输入 `min(3, 6-自然存量, 12-累计额外输入)`；容量满时跳过，错过的产额不存成欠款 |
| 自然容量 | 最多6，包含未预约和已预约未采部分；已采库存及作品另记 |
| 一次预约 | 固定3；只授予已有自然材料的采集资格，不立即进入库存 |
| 分配单位 | 服务端可信名册中的已知 `operatorId` 控制组；每组最多一份 queued 或 active |

## 身份来源与实验名册

当前 `WorldDatabase.Initialize` 把 a1/a2 都写为 `local-operator`；`Authenticate` 从会话关联的居民行读取归属。请求体不能覆盖身份，`issue-session` 只轮换既有角色凭据，不产生新控制主体。因此直接拿当前 a1/a2 做两个独立单位不成立。

最小可信来源是**创建新候选库时由研发方提供、校验并持久化的固定实验名册**。按构建方要求，建议保留 a1/a2 同属 `local-operator` 及原出生点，再增加零库存 a3，声明其属于 `research-late`、出生于东岸 `[28,17]`。分组在这个实验期间不可由 HTTP、重新登录、新 session 或角色输入改变；发行会话仍走既有离线管理路径。名册是测试输入，不是从行为猜出的人类身份，也不证明两个组在现实中独立。现有 r9 名册不重标。

若不扩展角色数量，可以先验证现有同组 a1/a2 共享一份，但仍缺少“一个组含多个角色，另一个组同时等待”的服务端验收；不能拿会话轮换代替多个 actor 的压力。建议新候选至少上述三角色，其他客户端是否需要调整由构建方裁定。隐藏共同控制、名册登记欺骗、跨组串谋继续未解决；不引入实名认证系统。

预约归属固定到请求的 actor，并同时记录其 operator。别名不能领取这份资格，也不能再占一份；这避免资格在组内转移又引入一套授权动作。已领取木材仍可依 r9 赠送。库存变少不会重置排队资格，赠送、建造和新会话均不能插队。

## 可实现的状态机与账本

建议最少保留：来源状态（开关、累计输入、自然存量、上次已处理生产周期）、持久服务时间、递增队列号、预约行（申请命令、operator、actor、source、状态、授予时刻、截止时刻、剩余可采量）。无需增加价格、债务、生产工具或通用任务调度系统。

| 当前状态 | 操作或时钟事实 | 结果 |
|---|---|---|
| 无有效请求 | reserve，组无 queued/active，预算能容纳 | queued，写固定队列号；个人库存不变 |
| queued | 后台按 FIFO 找到3份未预约自然材料 | active，固定预约 ID、owner actor、source、remaining=3、到期时间 |
| active | 原 owner 到达，gather 通过当前几何、身份、库存、期限校验 | 自然材料−1、本人库存+1、remaining−1；归零转 completed |
| queued/active | owner 显式 cancel | cancelled；只解除未采部分资格，不退库存、不改旧 gather 回执 |
| active | 时间达到截止点 | expired；释放 remaining 的资格，已采库存和作品不变 |
| completed/cancelled/expired | 同组用新的明确请求再申请 | 从队尾重新排；不能恢复旧序号、截止时间或原材料额度 |

同一原命令重复先查旧回执，返回原事实；新 commandId 不能绕过同组唯一有效请求。部分领取不续期。到期、授予、生产使用同一写事务中的当前时间和材料状态，避免同时采集与到期各算一次。建议一个时钟事务依次处理“到期释放 → 本周期输入 → 按 FIFO 授予”；没有材料变化的到期也须保留预约终态。

**有限预算必须有入队边界。** 定义 `Q` 为排队份数，`R` 为所有 active 的未采数量，`N` 为当前自然存量，`B` 为尚未输入的预算。仅当 `3Q + R + 3 <= N + B` 才接纳新的3份申请；否则给出明确来源预算不足，不能承诺无限排队后必有材料。这里 R 已包含在 N 中，左侧代表既有及新增需求，右侧代表目前及未来可供材料，不是把预约木材计算两遍。取消或到期会释放需求；已领取部分已离开 N，不会凭到期回来。

材料守恒式为：

```text
12 + 累计实际生态输入
= 旧树未采 + 采集区未预约自然材料 + 采集区已预约未采材料
  + 所有角色库存 + 所有作品体现材料
```

输入记录生态来源账户 → 采集区；gather 记录采集区 → 角色；赠送、建造沿用原账本。预约、取消、到期只改变资格，不记作新发行或库存返还。每次输入有不可重复的 `(instance, source, productionPeriod)` 标识，实际输入量、事件与 `issuedWood` 同事务提交。原节点的 `initialWood=3` 和 `remaining<=initial` 无须因此改写；新增来源应独立表达，不能伪装成旧树恢复。

## 服务时间、重启与原命令

建议服务时间只累计本实例服务进程运行的已确认时长，不计算关机时间，不读客户端时钟，不按 GET 次数推进。使用单调计时源计算进程内经过时间，并持久化累计值及已处理周期。重启从最后持久值继续；未提交的尾部时间可损失，不能重复发料。真实 UTC 可作审计显示，不能直接作为生产周期或到期判断。

.NET 的 `TimeProvider` 提供高精度时间戳，默认实现使用 Stopwatch；它本身不提供跨进程持久化或幂等输入。后台任务可采用 Hosted Service；不能把“计时回调运行过”当作“事务已提交”。[TimeProvider 官方说明](https://learn.microsoft.com/en-us/dotnet/standard/datetime/timeprovider-overview)、[运行时实现](https://github.com/dotnet/runtime/blob/main/src/libraries/Common/src/System/TimeProvider.cs)、[Hosted Service](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)。

建议约1服务秒检查一次。持久时间心跳可不制造居民动作；实际生产、授予、到期必须写可审计系统事件，并按契约更新业务版本。该事件没有虚构居民作者。时钟写入与居民写入仍须串行处理；SQLite `BEGIN IMMEDIATE` 可能返回 BUSY，锁冲突不能被记为已推进或已生产。[SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)。

每个实例只能有一个有效计时写入者。至少拒绝同一候选数据库的第二个服务进程；否则两个进程都累计自己的 elapsed，会把运行时间重复输入。具体互斥方式由构建方采用，不要求引入分布式协调。独立复制数据库后双写仍不在本轮保证内。

来源一次性开启建议确定为**停止服务后的显式离线管理事务**，不由普通居民动作、耗尽条件或登录自动触发。可新增 `enable-material-source --expected-instance <原实例ID>`，用既有 `WORLD_DATA_DIR` 定位库；仅打开已有 r10，先取得与时钟相同的独占锁，再校验实例并写开启事件、固定参数与剩余预算。缺库、错实例、旧规则或服务仍在运行均拒绝；不能调用新建路径补出一个库。重复开启返回已开启，不能重置周期、名册、预算或预约。

开启时持久化 `enabledAtServiceMs`，第一生产周期为该值+10000，后续按此原点计数；不能沿用世界启动以来的整十秒格点，让运行已久的空来源一启用就追补。后续重启自动延续既有状态。授予资格的60秒从**实际授予事务的当前服务时刻**开始，不能因计时回调延迟而回填到旧生产周期、导致刚看见的资格已经过期。测试时钟只在隔离故障测试入口开放，正常居民和生产配置不能提交“快进”。分别报告真实等待的烟测与可控时钟实验。

后台时间不能替换原命令恢复：新动作同样冻结规则、实例、actor、原 commandId 和预算；503/丢响应仍先查原回执。新预约命令可沿用已采用的 actor-state 模式，让无关居民行走和系统生产不单因全局版本增加就阻止入队；本人后续动作、收到赠送等原失效条件保留。过期的 gather 只能明确停止，不能自动换新的预约或命令继续。

新采集回执应携带原预约引用、源、实际采集量、该预约采集前后 remaining、库存前后与事件引用。**不要直接放宽旧 gather 的余量证据。** r8/r9 的树余量只减；新自然池可在请求期间增加，不能用池总量与旧观察比较来证明本次采集。新分支应核对固定预约自己的 remaining（只减且最多3）和库存变化；旧树分支保留原规则。首次 reserve 的权限、命令数、查询数、超时、后续 gather/build 的预算必须在任务中明确冻结。

## 空间与同实例连续性

此前48条实际 r8 HTTP 命令已证明四个旧树位可以全部变成合法平台；条件分析也证明“只用旧树位、跳过既有建筑、不新增地点”的来源可能为零。不能通过恢复阻挡树、删除平台、搬走居民或追溯撤销合法作品解决。

建议的 `[28,10]` 采集区与四个旧树位平台及现有岩石均不重叠。它始终可走，空时仍明确保留建造边界；建造验证对该矩形作占地检查，视觉上显示边界，不把它画成可建空地。原地形碰撞、桥和其他平台保持原行为。

以旧 HTTP 已建桥 `[18,12]` 和耗尽树状态输入当前 Python 路径函数，`[5,7]` 到来源路径24.095米，`[26,17]` 到来源7.280米，所有路径段通过现有 clear 检查。按3米/秒的纯运动下限分别8.032秒和2.427秒。**这是现有路径函数的候选坐标探针，未走实际 r10 命令，不是60秒租期足够的最终证明。** 无桥时西岸仍未保证入口；本轮前置条件就是公共桥已建。新平台目标 `[28,16]` 与采集区分离，但最终仍须实际 build 校验，不能由路径计算代替。

同实例实验推荐顺序：创建来源关闭的 r10 候选 → 从零库存真实采完旧12木材 → 真实建6木材公共桥，早期方保留6并拒绝赠送 → 保存实例、桥、库存、回执指纹 → 在**同一个库和实例**开启上述有限来源 → 后来者 reserve、行走、逐次 gather 3、build 自己的平台 → 核对早期6库存与原桥、原回执仍在。新造平台消耗3，只能来自新增输入，不借用拒绝方材料。

这一方法验证新候选实例内来源开启前后的连续历史，**不验证现有 r9 升级到 r10**。旧 r8/r9 原样运行，不能把复制或重建新库称为迁移；将来升级旧世界还需单独处理场景、schema、版本、旧 pending 和回执。当前 clients 中 r8/r9 白名单、世界绑定与共享恢复记录必须增加明确新能力分支；遇到旧二进制读不懂的未来记录不能静默丢弃。参见 [13 的恢复边界](13-transfer-adoption-review.md)。

## 本轮离线结果与实际验收要求

本轮私有模型5个情形均通过材料和预约约束：

| 情形 | 候选模型结果 |
|---|---|
| early 先领3，再赠给别名、重新申请 | late 在第20服务秒获资格；early 第二次在30秒 |
| early 先领3，再消费3、重新申请 | 同上；消费不重置优先级 |
| early 的32个已知别名竞争，late 等待 | early 只接纳1份，31次重复拒绝；late 在20秒获资格 |
| early 领1后停止，late 持有3未领，third 排队 | early 在70秒释放剩2；third 同时取得3；已采1仍归 early |
| 4组先后各领3并消费，累计输入12用尽 | 第5份申请明确拒绝，未留下无法兑现的排队承诺 |

这些时间来自离散候选模型，从服务时间0开始排队、首批在10秒产生。实际调度、HTTP、移动、库存上限与建造仍须真实验证。私有证据 `.local/research/material-source-contract/20261026T041500Z/{probe.py,results.json}`；实际世界命令0、服务进程0、模型调用0。该探针不替代来源持久化、事务故障、身份授权或客户端验收。

建议实际验收重点如下，避免扩成宏观经济测试：

1. **拒绝方不配合的完整目标。** 按上述同实例初态运行，记录首次请求、成功入队、授予、到达、第三次采集、平台提交六个时点；原桥和拒绝方6库存保留。不能只显示预约成功或库存数字。
2. **竞争与身份。** 同组多 actor、多 session、多 commandId；取得材料后 gift/spend 再申请；新同组请求不能越过已成功排队的 late。只授予一种名册下的条件保证，不能声称已识别现实独立人。
3. **到期与原回执。** 部分采1、停服/重启、到期释放2；旧已提交采集查询原回执，未知采集恢复原 ID；未提交而已到期的原 gather 明确拒绝。取消、到期、采集竞争不能双扣或返还已采材料。
4. **来源与时钟。** 满容量包含预约量，GET 连续轮询不生产；正常真实等待跨两个周期；重启不离线补发，重复周期不增发，预算耗尽明确拒绝。生产前/提交后退出分别证明回滚与已提交事实，拒绝双计时进程。
5. **空间与客户端。** 旧树位平台仍可走；采集区空/满都可走且都禁止新建筑侵入；Godot 与任务执行器均经正式 API 完成 reserve→gather→build，预算、授权、原起点、恢复记录及实际作者完整。

两组从激活时入队的理想模型在20服务秒内授予 late；实际报告须列时钟检查粒度和调度延迟。一般排队必须附带已接纳的预算、前方份数、到期规则和可达条件，不能把20秒扩成任意人口的承诺。停服、写入受阻或进程未被调度时也没有真实墙钟上限。最终能宣称的只是：声明人口、预算、时间和空间条件下，持有者拒绝赠送仍有一条实际基础创作路径。长期先发差距与更广泛垄断约束继续待验证。
